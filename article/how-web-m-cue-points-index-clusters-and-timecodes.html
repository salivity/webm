How WebM Cue Points Index Clusters and Timecodes

WebM cue points serve as a built-in search index that enables efficient, frame-accurate seeking within media streams. Based on the Matroska (MKV) container specification, WebM uses the Cues element to map specific playback timestamps to exact physical byte offsets in the file and correlate them with internal block-level timing structures. This article breaks down how WebM structures its CuePoint elements to reference both the target cluster's byte location and the relative timecodes of internal blocks.

The Role of the Cues Element

In WebM, media data is divided into chunks called Clusters, and each cluster contains one or more audio or video blocks (typically stored as SimpleBlock or BlockGroup elements). To prevent media players from parsing the entire stream sequentially to find a specific playback position, WebM includes an optional but critical Cues element.

The Cues element contains multiple CuePoint entries, where each entry indexes a specific point in time (often keyframes) for random access.

Indexing the Absolute Timestamp: CueTime

Each CuePoint contains a mandatory CueTime element:

  • CueTime: Represents the absolute presentation timestamp of the indexed frame, expressed in container timecode units (governed by the global TimestampScale, typically milliseconds).

When a player requests a seek to a specific time, the demuxer searches the CuePoint list to find the closest CueTime that occurs at or before the requested position.

Locating the File Offset: CueClusterPosition

Under each CuePoint, one or more CueTrackPositions elements specify the spatial and structural location of the indexed track's data:

  • CueTrack: The track number associated with the cue point.
  • CueClusterPosition: An integer indicating the byte offset of the target Cluster element containing the relevant block. This offset is measured relative to the start of the Segment element's data payload.

By reading CueClusterPosition, the demuxer can instantly seek its byte stream pointer to the exact start of the required Cluster without reading the preceding payload data.

Resolving the Relative Block Timecode

A WebM Cluster has its own base Timestamp header. Within the Cluster, individual SimpleBlock elements do not store absolute presentation timestamps; instead, they store:

  1. Track Number: Identifies the stream.
  2. Relative Timecode: A signed 16-bit integer representing the block's time offset relative to the parent Cluster's base Timestamp.
  3. Flags: Marking keyframes, discardable frames, and invisible frames.

The absolute presentation time of any block is calculated as: \[\text{Absolute Block Time} = \text{Cluster Timestamp} + \text{Block Relative Timecode}\]

To pinpoint the exact block within the cluster, CueTrackPositions can optionally include:

  • CueRelativePosition: The byte offset inside the Cluster payload where the target Block or BlockGroup starts.
  • CueBlockNumber: The sequential block number within the Cluster.

The Seeking Process in Practice

When seeking using WebM cue points, the demuxer executes the following steps:

  1. Index Lookup: Searches CuePoint entries for the target timestamp (CueTime).
  2. Byte Jump: Reads CueClusterPosition and seeks directly to that byte offset in the file to read the target Cluster.
  3. Base Timecode Extraction: Parses the Cluster's header to obtain its base Timestamp.
  4. Block Navigation: Reads through the cluster (or jumps directly via CueRelativePosition) to locate the keyframe block whose relative timecode, when added to the Cluster's base timestamp, matches the expected CueTime.
  5. Decoding: Feeds the keyframe block to the video decoder to immediately resume playback.
