How CDNs Cache WebM with Byte-Range Requests

Content Delivery Networks (CDNs) leverage HTTP byte-range requests to optimize the delivery and caching of WebM video files without requiring physical file fragmentation. By requesting and storing specific byte offsets rather than entire video files, CDNs can serve media segments dynamically, reduce origin load, improve time-to-first-frame, and seamlessly handle playback scrubbing. This article explains how byte-range requests interact with the WebM container format and the mechanisms CDNs use to cache and deliver these media segments efficiently.

Understanding WebM Structure and Byte Ranges

The WebM container format is based on Matroska (EBML) and organizes media data into discrete headers, cues (indexes), and clusters of video and audio blocks. When a modern browser plays a WebM stream—frequently via Media Source Extensions (MSE)—it does not need to download the full media asset at once.

Instead, the browser:

  1. Requests the initial header and index bytes to parse metadata.
  2. Identifies the byte offsets for specific timecodes using the WebM cue points.
  3. Issues HTTP Range requests (e.g., Range: bytes=1048576-2097151) to fetch only the clusters required for immediate playback or seeking.

How CDNs Intercept and Slice Range Requests

When a user requests a byte range, modern CDN edge nodes process the request using a technique known as range slicing or partial-content caching:

  • Sub-Range Alignment: Rather than passing arbitrary client byte offsets directly to the origin, the CDN edge divides the target file into standardized, contiguous blocks (typically 1 MB to 8 MB per slice).
  • Targeted Origin Fetching: If a client requests bytes 1,500,000 to 2,500,000, the CDN maps this range to the corresponding internal slice(s). It queries the origin only for missing slices using standard Range headers, leaving existing cached slices untouched.
  • HTTP 206 Partial Content Assembly: Once the CDN possesses the required slices, it extracts the exact byte range requested by the client, formats the response with an HTTP/1.1 206 Partial Content status code and a Content-Range header, and delivers it to the user.

Key Efficiency Benefits

1. Single Asset Management on the Origin

Unlike segmented protocols like traditional HLS or MPEG-DASH—which often store thousands of individual .m4s or .ts chunk files on the origin—WebM with byte-range requests requires only a single contiguous .webm file. The CDN creates the segmentation layer virtually on the edge, reducing origin file-system overhead and simplifying asset storage.

2. Efficient Seeking and Reduced Bandwidth Waste

When users seek forward in a video or abandon playback early, requesting full media files leads to wasted bandwidth. Byte-range caching ensures that only the clusters surrounding the user's active playback position are fetched from the origin and cached at the edge, drastically reducing origin egress costs.

3. High Cache Hit Ratios for Popular Segments

Standardizing byte-slice sizes across the CDN ensures that different users watching the same video contribute to the same cache footprint, even if their players request slightly different offsets. The video initialization segment (containing the EBML header and cues) and the opening clusters achieve near-permanent edge residency due to high reuse across all viewing sessions.

4. Collapsed Forwarding

If multiple clients simultaneously request different or overlapping ranges of a WebM file that is not yet fully cached, CDNs use request collapsing. The edge node combines simultaneous requests for the same slice into a single upstream request to the origin, preventing traffic spikes and buffering delays.
