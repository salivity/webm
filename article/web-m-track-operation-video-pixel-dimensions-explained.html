WebM TrackOperation Video Pixel Dimensions Explained

In WebM and Matroska container formats, video pixel dimensions for complex or combined tracks are defined through a combination of the TrackOperation element and the standard Video settings within the track header. This article explains the EBML structural hierarchy, how TrackOperation handles multi-source streams such as 3D stereoscopic video, and how PixelWidth and PixelHeight determine the rendered output.

The EBML Track Hierarchy

WebM relies on Extensible Binary Meta Language (EBML). All track configurations are nested under the Segment container inside the Tracks master element. Each individual video stream is defined by a TrackEntry (0xAE).

When a track utilizes TrackOperation (0xE2), it functions as a virtual or composite track created from one or more source tracks.

Segment (0x18538067)
└── Tracks (0x1654AE6B)
    └── TrackEntry (0xAE)
        ├── Video (0xE0)
        │   ├── PixelWidth (0xB0)
        │   ├── PixelHeight (0xBA)
        │   ├── DisplayWidth (0x54B0)
        │   └── DisplayHeight (0x54BA)
        └── TrackOperation (0xE2)
            └── TrackCombinePlanes (0xE3)
                └── TrackPlane (0xE4)
                    ├── TrackPlaneUID (0xE5)
                    └── TrackPlaneType (0xE6)

How Pixel Dimensions Are Defined

Pixel dimensions are not stored directly inside the TrackOperation element itself. Instead, the final output dimensions and the source dimensions are defined at two distinct levels:

1. Composite Track Dimensions (The Video Element)

The parent TrackEntry containing the TrackOperation defines the total pixel dimensions of the final composed video frame. These are set using standard EBML video elements:

  • PixelWidth (0xB0): An unsigned integer defining the width of the encoded video frame in pixels.
  • PixelHeight (0xBA): An unsigned integer defining the height of the encoded video frame in pixels.

These values inform the demuxer and decoder of the target canvas size after all operations defined in TrackOperation have been executed.

2. Source Track Mapping (TrackOperation and TrackCombinePlanes)

Inside TrackOperation, the TrackCombinePlanes (0xE3) element specifies how distinct source tracks are merged to form the composite image (commonly used for stereoscopic 3D, combining left and right eye channels):

  • TrackPlane (0xE4): Contains the configuration for a single plane.
  • TrackPlaneUID (0xE5): References the unique ID (TrackUID) of the source track providing data for this plane.
  • TrackPlaneType (0xE6): Defines the role of the plane (e.g., left eye, right eye, or background).

Each source track referenced by TrackPlaneUID has its own independent TrackEntry containing its own PixelWidth and PixelHeight. The demuxer uses the source tracks' pixel dimensions to decode each stream individually before mapping or scaling them into the final canvas dimensions specified by the composite TrackEntry.

Display Dimensions vs. Coded Dimensions

If non-square pixels or specific anamorphic scaling are used in conjunction with TrackOperation, WebM uses display dimension elements located alongside the pixel dimension elements:

  • DisplayWidth (0x54B0): The intended display width in scaled units.
  • DisplayHeight (0x54BA): The intended display height in scaled units.
  • DisplayUnit (0x54B2): Defines the measurement system (pixels, centimeters, inches, or aspect ratio).

While PixelWidth and PixelHeight dictate the raw decoded buffer size of the combined track, DisplayWidth and DisplayHeight instruct the video renderer how to scale the output to achieve the correct aspect ratio during playback.
