WebRTC Bandwidth Estimation for WebM Codecs

WebRTC uses dynamic bandwidth estimation (BWE) to deliver smooth real-time video over fluctuating network conditions. When handling WebM-compatible codecs—primarily VP8 and VP9—WebRTC implementations rely on congestion control mechanisms to calculate available capacity and adapt encoder settings on the fly. This article covers the primary bandwidth estimation algorithms paired with WebM video codecs, how they operate, and how they control codec output.

Google Congestion Control (GCC)

Google Congestion Control (GCC) is the default and most widely implemented bandwidth estimation framework used with WebM codecs in WebRTC. Standardized through the IETF, GCC combines delay-based and loss-based metrics to estimate network throughput. GCC operates in two historical and modern modes:

1. Sender-Side BWE (Transport-Wide Congestion Control)

Modern WebRTC deployments predominantly use sender-side bandwidth estimation via Transport-Wide Congestion Control (TWCC).

  • Mechanism: The receiver attaches a small sequence number to incoming RTP packets and periodically sends RTCP feedback messages detailing the exact arrival time of each packet.
  • Calculation: The sender analyzes the delay gradients (inter-arrival vs. inter-send time). If packet delay begins to climb, GCC detects early queuing at the network bottleneck before actual packet loss occurs and reduces the target bitrate.
  • Loss-based Fallback: If packet loss is detected without prior delay spikes, GCC scales down the target bitrate according to a predefined loss threshold.

2. Receiver-Side BWE (REMB)

Before TWCC became the standard, WebRTC relied on Receiver Estimated Maximum Bitrate (REMB).

  • Mechanism: The receiving endpoint ran the delay-based estimation algorithm internally, calculating the maximum supportable bitrate.
  • Signaling: The receiver then sent an RTCP REMB feedback message back to the sender containing the computed bitrate limit. While largely superseded by TWCC due to sender-side flexibility and faster adaptation, REMB is still supported as a fallback for legacy endpoints streaming VP8.

Alternative Bandwidth Estimation Algorithms

While GCC is the default in browser engines like Chromium, specialized WebRTC implementations and custom media servers occasionally pair WebM codecs with alternative algorithms:

  • BBR (Bottleneck Bandwidth and RTT): Developed by Google, BBR builds an explicit model of the network path by measuring maximum delivery rate and minimum round-trip time (RTT). Adapted variants of BBR for real-time video minimize latency while avoiding queue buildup.
  • SCReAM (Self-Clocked Rate Adaptation for Multimedia): An IETF-standardized algorithm (RFC 8298) designed for conversational media. SCReAM uses delay-based feedback and handles L4S (Low Latency, Low Loss, Scalable Throughput) environments effectively.
  • NADA (Network-Assisted Dynamic Adaptation): Standardized under RFC 8593, NADA utilizes delay, packet loss, and explicit congestion notifications (ECN) to balance link utilization and delay constraints.

How WebM Codecs React to BWE Outputs

Bandwidth estimation feeds directly into the WebM encoding pipeline, which responds through structural rate control:

VP8 Bitrate Adaptation

VP8 typically leverages temporal scalability and simulcast to adapt to GCC calculations:

  • Temporal Layering: Drops higher temporal layers when BWE drops, reducing frame rate without dropping keyframes.
  • Simulcast: The sender generates multiple streams of different resolutions and bitrates. Based on BWE feedback, the selective forwarding unit (SFU) or sender switches to the appropriate stream.

VP9 Bitrate Adaptation

VP9 provides native Scalable Video Coding (SVC), offering finer-grained adaptation based on BWE:

  • Spatial Scalability: VP9 encodes multiple spatial resolutions into a single stream. If BWE drops, the encoder or SFU drops upper spatial layers instantly without needing a new keyframe.
  • Dynamic Quantization: The VP9 encoder dynamically adjusts its Quantization Parameter (QP) to match the exact bits-per-second budget supplied by the BWE module.
