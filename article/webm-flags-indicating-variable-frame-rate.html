WebM Flags Indicating Variable Frame Rate

This article provides an overview of how the WebM container format indicates a non-constant or variable frame rate (VFR) stream. Because WebM is built on the Matroska (MKV) specification, timing operates fundamentally on individual frame timestamps rather than a fixed frame counter. Readers will learn which specific EBML elements, container properties, and timestamp structures distinguish a variable frame rate from a constant frame rate (CFR) in WebM video tracks.

The Native Timing Architecture of WebM

WebM does not feature a dedicated boolean flag explicitly labeled "is_vfr." Instead, the Matroska/EBML architecture is designed as natively variable frame rate. Every frame in a WebM file is packed inside a SimpleBlock or BlockGroup that carries its own explicit timestamp relative to the parent Cluster element's Timestamp. As a result, CFR is treated as a specific subset of VFR where the intervals between timestamps happen to remain identical.

The DefaultDuration Element

The primary container-level indicator of frame timing consistency resides inside the TrackEntry element (0xAE) for the video track:

  • Element Name: DefaultDuration
  • Element ID: 0x23E383
  • Type: Unsigned Integer (nanoseconds per frame)

In a strictly Constant Frame Rate (CFR) WebM file, DefaultDuration is defined and explicitly populated with the length of a single frame in nanoseconds (for instance, 16666666 for approximately 60 frames per second, or 41708333 for 23.976 frames per second).

In a non-constant frame rate (VFR) stream, the container indicates variability through two main configurations:

  1. Omission of DefaultDuration: When encoding in VFR mode, encoders (such as libvpx or FFmpeg) frequently omit the DefaultDuration element entirely from the video TrackEntry. Its absence indicates to the demuxer that frames do not possess a fixed temporal duration and playback timing must rely strictly on individual block timestamps.
  2. DefaultDuration as a Nominal Fallback: In some encoders, DefaultDuration is populated with an average or nominal value for container compatibility, but the frame timestamps intentionally deviate from this interval.

Block-Level Timestamps

Because the container elements themselves only describe track metadata, definitive detection of a non-constant framerate requires reading the timestamps stored in the media payload:

  • TimestampScale (or TimecodeScale): Located in the Info segment (0x1549A966), this element specifies the base unit of time for the file, defaulting to 1,000,000 nanoseconds (1 millisecond).
  • Cluster Timestamp: Located at the start of each Cluster (0x1F43B675), indicating the cluster's base presentation time.
  • Block Relative Timestamp: Every SimpleBlock (0xA3) contains a 16-bit signed integer defining its presentation offset relative to its parent cluster's timestamp.

A WebM stream is confirmed to be non-constant framerate if the delta between consecutive frame timestamps (\(T_{n+1} - T_n\)) varies across the stream. If the calculated durations deviate from each other, demuxers treat the stream as VFR regardless of any metadata flags present in the track headers.
