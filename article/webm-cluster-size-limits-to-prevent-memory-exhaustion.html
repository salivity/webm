WebM Cluster Size Limits to Prevent Memory Exhaustion

WebM demuxers must safely handle EBML-encoded video streams without allocating unbounded memory when encountering maliciously crafted or corrupt files. This article covers the exact binary encoding mechanisms of WebM clusters, the mathematical limits imposed by the Extensible Binary Meta Language (EBML) Variable-Size Integer (VINT) specification, and the concrete implementation thresholds required to prevent out-of-memory (OOM) denial-of-service vulnerabilities.

The Binary Structure of a WebM Cluster

In WebM (a subset of the Matroska specification), video and audio data are grouped inside Cluster elements. A Cluster begins with a 4-byte Element ID, followed by an EBML Variable-Size Integer (VINT) that declares the byte length of the cluster's payload:

  • Cluster ID: 0x1F 0x43 0xB6 0x75
  • Cluster Size (VINT): A variable-length field ranging from 1 to 8 octets.

A VINT denotes its own length via leading zero bits followed by a terminating 1 bit marker:

Octets Length Descriptor Mask Maximum Encoded Size (Bytes)
1 1xxxxxxx \(2^7 - 2 = 126\)
2 01xxxxxx \(2^{14} - 2 = 16,382\)
3 001xxxxx \(2^{21} - 2 \approx 2.09 \times 10^6\)
4 0001xxxx \(2^{28} - 2 \approx 2.68 \times 10^8\) (256 MiB)
8 00000001 \(2^{56} - 2 \approx 7.20 \times 10^{16}\) (~72 PiB)

The theoretical maximum size representable in an 8-octet VINT is \(2^{56} - 2\) bytes. If a parser attempts to read the size field and immediately allocate a buffer based on this declared length, any value above a few megabytes can exhaust system memory or trigger signed integer wrap-around errors.

The Unknown Size Indicator

The EBML specification reserves a special bit pattern where all data bits in a VINT are set to 1. This indicates an Unknown Size (often used for live streaming where total cluster duration is not known ahead of time):

  • 1-byte VINT: 0xFF
  • 2-byte VINT: 0x7F 0xFF
  • 4-byte VINT: 0x1F 0xFF 0xFF 0xFF
  • 8-byte VINT: 0x01 0xFF 0xFF 0xFF 0xFF 0xFF 0xFF 0xFF

When an Unknown Size token is present, demuxers must never attempt to pre-allocate memory. Instead, demuxers must parse sub-elements incrementally until encountering another top-level EBML ID (such as the next Cluster 0x1F43B675 or a Cue element 0x1C53BB6B).

Defensive Binary Limits for Demuxer Implementations

Production-grade demuxers (such as those in Chromium and FFmpeg) enforce strict binary boundaries to neutralize memory exhaustion vectors:

1. Maximum VINT Size for Cluster Payloads

While the EBML specification permits 8-byte VINTs, WebM implementations commonly restrict the maximum valid size of an individual Cluster to values that fit within standard memory architectures:

  • Binary Limit: Parsers should cap cluster payload sizes to a maximum of \(2^{31} - 1\) (2,147,483,647 bytes) to avoid 32-bit signed integer overflow.
  • Practical Limit: Typical WebM clusters hold between 1 to 5 seconds of media. Standard-compliant video streams rarely require a cluster exceeding 32 MiB to 64 MiB (0x02000000 to 0x04000000), even at 4K resolution.

2. Frame-Level Allocation Limits (SimpleBlock / Block)

A cluster contains individual SimpleBlock (0xA3) or BlockGroup (0xA0) elements. Pre-allocating memory for these sub-elements poses the highest risk of heap exhaustion:

  • Max Single Frame Limit: Chromium enforces a strict threshold on individual frame buffers, rejecting or dropping blocks whose declared size exceeds 32 MiB to 100 MiB.
  • Any single block with a declared size larger than the remaining bytes in the parent Cluster must be rejected immediately as malformed.

3. Zero Upfront Allocation Rule

To remain immune to cluster-level OOM exploits:

  • Never allocate based on the Cluster size header. The cluster is a container element; only leaf elements (raw video/audio packets inside blocks) require allocated memory.
  • If a Cluster specifies an explicit size that extends beyond the end of the file or streaming window, it must be flagged as truncated without pre-allocating the missing bytes.
  • An Unknown Size VINT must only be accepted for container elements like Cluster and Segment, and must be rejected with a parse error if encountered on primitive data types or blocks.
