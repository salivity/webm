How MPV Handles Custom Shaders on WebM Video

The MPV media player processes custom GLSL shaders on WebM videos through its high-performance, GPU-accelerated rendering pipeline (--vo=gpu or --vo=gpu-next). When playing a WebM container, MPV demuxes the stream, decodes the underlying video tracks (typically VP8, VP9, or AV1), and uploads the decoded pixel frames to the GPU as native textures. From there, user-defined shader programs intercept and modify these textures at specific stages—such as during chroma upscaling, color space conversion, or final presentation—allowing real-time post-processing without altering the source file.

Video Demuxing and Decoding to GPU Textures

A WebM file serves as a container based on Matroska. When MPV opens a WebM file, it relies on FFmpeg libraries (libavformat and libavcodec) or hardware-accelerated APIs (such as VA-API, NVDEC, or D3D11VA) to extract and decode the video bitstream.

Once decoded, the video frames exist as raw pixel data—frequently in planar YUV formats such as YUV420p. MPV transfers these raw planar buffers directly into GPU video memory (VRAM) as standard 2D textures. Because MPV decouples container demuxing from video rendering, WebM files are treated identically to MP4 or MKV files once their frames reach the GPU surface.

The Shader Execution Pipeline

MPV uses an internal rendering framework, largely powered by libplacebo in newer builds, to manage the processing pipeline. Custom shaders in MPV are written in a specialized GLSL format wrapped in .hook files. These files declare specific pipeline stages where custom code should run using direct hook directives:

  • LUMA and CHROMA Hooks: The shader runs directly on the separated native Y (luminance) or UV (chrominance) planes before they are merged or scaled. This stage is commonly used for specialized de-noising, line thinning, or custom chroma reconstruction.
  • RGB Conversion Hook: MPV applies standard color matrix transformations (e.g., BT.601, BT.709, or BT.2020) to convert YUV surfaces into linear or non-linear RGB textures. Shaders hooked at the RGB stage manipulate the fully combined color data.
  • SCALED and MAIN Hooks: These shaders execute during or immediately after the video is upscaled or downscaled to fit the target window resolution. Algorithms such as FSRCNNX, Anime4K, or custom sharpening filters operate at this stage.

Texture Sampling and Data Passing

When a custom shader is triggered, MPV generates and compiles a complete GLSL program dynamically:

  1. Binding: MPV binds the current video surface (or intermediate off-screen framebuffers) as input textures accessible to the shader via standard sampler uniforms.
  2. Coordinate Transformation: The player provides uniform variables defining source texture sizes, target dimensions, and pixel offsets, allowing shaders to sample neighboring texels accurately.
  3. Offscreen Rendering: If a shader generates an output texture intended for a subsequent shader pass, MPV renders the output directly to an allocated off-screen framebuffer object (FBO).
  4. Final Composition: After all active custom hooks finish executing, the resulting texture is passed to MPV's final display stage, where color management, tone mapping (for HDR WebM/VP9 content), and on-screen display (OSD) overlays are applied before presenting the frame to the display window.

Configuration and Performance

To apply a custom shader on top of a WebM playback surface, users pass the file path to the shader via the command line or mpv.conf:

--vo=gpu-next
--glsl-shader="path/to/shader.hook"

Because all operations occur within GPU shaders, the overhead of rendering custom effects onto WebM surfaces is dictated primarily by the complexity of the shader algorithms and the GPU's compute capability, eliminating CPU bottlenecks during playback.
