WebM EBML DocType and DocTypeVersion Constraints

This article provides an overview of the strict technical constraints placed on the DocType and DocTypeVersion fields within the Extensible Binary Meta Language (EBML) header of a WebM container. It outlines the required values, data types, and parser expectations defined by the WebM container specification to ensure cross-platform compatibility and proper media parsing.

The Role of the EBML Header in WebM

Every WebM file begins with an EBML header, which describes the encoding format and structural parameters of the container itself. Within this header, identity and versioning fields instruct demuxers on how to interpret the subsequent payload elements.

Constraints on the DocType Field

The DocType element (EBML ID 0x4282) specifies the exact document type format wrapped inside the EBML container.

  • Exact String Value: The value must be set strictly to the ASCII string "webm".
  • Case Sensitivity: The string is strictly lowercase. Values such as "WebM", "WEBM", or "matroska" are invalid in a conformant WebM file.
  • String Termination: The string should not contain extraneous whitespace or null-byte padding beyond standard EBML string encodings.
  • Parser Action: If a demuxer reads any value other than "webm", it must reject the file or treat it as a generic Matroska (MKV) container rather than standard WebM.

Constraints on the DocTypeVersion Field

The DocTypeVersion element (EBML ID 0x4287) indicates the specific version of the WebM specification used to encode the file.

  • Data Type: An unsigned integer (uint).
  • Permitted Values: The value must be set to 2 or 4, corresponding to the WebM profile features implemented in the container. WebM containers generally use version 2 for baseline features, while extended capabilities (such as elements introduced in newer Matroska specifications that WebM adopts) use version 4.
  • Specification Alignment: The value written must reflect the highest version of any WebM feature utilized within the file.

Relationship with DocTypeReadVersion

While DocTypeVersion indicates the full specification version used to create the file, WebM headers also require the DocTypeReadVersion element (EBML ID 0x4285):

  • Compatibility Enforcement: DocTypeReadVersion is typically set to 2.
  • Parser Enforcement: A WebM parser must check that its own supported version is greater than or equal to DocTypeReadVersion. If the parser's supported version is lower than DocTypeReadVersion, the parser must abort reading the file.
