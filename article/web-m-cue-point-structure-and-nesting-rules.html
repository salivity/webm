WebM CuePoint Structure and Nesting Rules

In WebM media files, the Cue table serves as an index for efficient seeking, relying on structured CuePoint elements to map presentation timestamps to precise byte offsets within video clusters. This article explains the structural and Extensible Binary Meta Language (EBML) nesting rules that govern CuePoint elements, detailing their position within the file hierarchy, required child elements, and internal payload organization.

Hierarchical Position of the Cues Element

WebM is a restricted subset of the Matroska (MKV) container format, governed by EBML syntax. At the container level, the index hierarchy is defined as follows:

  1. Segment Element (0x18538067): The top-level root container containing all metadata, cluster data, and seek tables.
  2. Cues Element (0x1C53BB6B): A Level 1 element placed directly inside the Segment. It acts as the parent array containing all individual cue markers.
  3. CuePoint Element (0xBB): A Level 2 element nested directly inside Cues. A single Cues block contains one or more CuePoint entries.
Segment (Level 0)
└── Cues (Level 1)
    ├── CuePoint (Level 2)
    ├── CuePoint (Level 2)
    └── ...

Direct Child Elements of CuePoint

Every CuePoint element must define specific child elements (Level 3) to be valid under the WebM specification:

  • CueTime (0xB3): A mandatory unsigned integer representing the absolute timestamp (scaled by TimestampScale) of the cue point. Each CuePoint must contain exactly one CueTime.
  • CueTrackPositions (0xB7): A mandatory Master element that groups track-specific location metadata. Each CuePoint must contain at least one CueTrackPositions element.

Nesting Within CueTrackPositions

The CueTrackPositions element contains Level 4 sub-elements that provide exact data locations:

  • CueTrack (0xF7): A mandatory unsigned integer identifying the TrackNumber to which this cue position applies.
  • CueClusterPosition (0xF1): A mandatory unsigned integer representing the byte offset from the start of the Segment payload to the beginning of the Cluster containing the referenced frame.
  • CueRelativePosition (0xF0): An optional unsigned integer indicating the offset within the cluster to the specific Block or SimpleBlock.
  • CueBlockNumber (0x5378): An optional unsigned integer indicating the sequential block number inside the cluster.
  • CueDuration (0xB2): An optional unsigned integer indicating the duration of the referenced block.

Structural and Ordering Constraints

  • Sequential Time Ordering: CuePoint elements must be sorted in ascending order based on their CueTime values to allow binary search during playback.
  • Keyframe Association: In WebM, each CuePoint typically references a keyframe (I-frame) to ensure decoders can start playback immediately at the targeted offset without referencing previous frames.
  • Multi-Track References: While a CuePoint requires at least one CueTrackPositions, it may contain multiple CueTrackPositions entries if synchronization data across multiple tracks (such as simultaneous video and audio cue targets) is required at the exact same CueTime.
