WebM Timestamp Rollover in Long Live Streams

This article explains how the WebM container format manages timestamps during continuous, multi-day live streams. It details the structural design of Extensible Binary Meta Language (EBML), the interplay between Cluster-level and Block-level timestamps, why WebM avoids the frequent rollover issues common to other container formats like MPEG-TS, and how client-side playback pipelines handle long-running streams.

EBML and 64-Bit Timestamp Architecture

WebM is a subset of the Matroska (MKV) multimedia container format, which is built on EBML (Extensible Binary Meta Language). At the container level, WebM handles presentation timing using a global timebase defined in the Segment Info element called TimestampScale (historically TimecodeScale). By default, this value is set to 1,000,000 nanoseconds, providing a 1-millisecond resolution.

The primary mechanism that prevents rollover in multi-day streams is the variable-length unsigned integer format defined by EBML. Cluster timestamps in WebM can use up to 8 bytes (64 bits). Even at a millisecond resolution, a 64-bit unsigned integer takes approximately 584 million years to overflow. Unlike MPEG-TS, which uses a 33-bit Program Clock Reference (PCR) running at 90 kHz that rolls over roughly every 26.5 hours, a properly configured WebM stream will not experience an integer overflow at the container level during any practical live stream duration.

Cluster Generation and 16-Bit Block Offsets

While the absolute timestamp of each Cluster uses a large integer, individual media frames inside each Cluster do not store absolute timestamps. Instead, Block or SimpleBlock elements contain relative timestamps stored as signed 16-bit integers.

At the standard 1-millisecond scale, a signed 16-bit integer has a range of -32,768 to +32,767 milliseconds (approximately ±32.7 seconds). To prevent this smaller relative counter from overflowing:

  1. The encoder or muxer must regularly close the active Cluster and open a new one.
  2. In typical live streaming configurations, a new Cluster is created at every keyframe (GOP boundary), typically every 1 to 4 seconds.
  3. Each new Cluster updates the absolute baseline timestamp, resetting the 16-bit relative counter for subsequent blocks back near zero.

As long as the distance between Clusters does not exceed ~32 seconds, the 16-bit relative offset never encounters an overflow.

Continuous Segments with Unknown Duration

For non-stop live broadcasting, WebM handles continuity by emitting an "unknown" or indefinite length for the primary Segment element. When the Segment length is omitted or set to an unknown EBML value, the muxer continuously appends new Clusters sequentially without needing to rewrite header elements or define a fixed endpoint.

Because timestamps inside successive Clusters advance monotonically, decoders interpret the incoming media stream as an uninterrupted timeline without triggering discontinuous presentation timestamps (PTS) jumps.

Client-Side Playback and Media Source Extensions (MSE)

While the WebM container itself does not roll over, playback engines—especially web browsers utilizing Media Source Extensions (MSE)—can encounter issues with memory management and continuous timeline tracking over several days.

In browser environments, continuous streams are typically delivered in segmented WebM chunks (e.g., via DASH or custom chunked HTTP pipelines). To prevent browser pipelines from running into floating-point precision limits or memory leaks during multi-day runs:

  • Buffer Eviction: Players configure the SourceBuffer to remove previously played segments from memory using removal algorithms (SourceBuffer.remove()).
  • Timestamp Offset Management: In segmented architectures, delivery pipelines can reset timestamps per segment or period using the MSE timestampOffset property, mapping container-level timestamps to an arbitrary player presentation timeline.
  • Period Boundaries: When using standards like MPEG-DASH with WebM segments, multi-day streams often divide broadcasts into distinct Periods, allowing timestamp baselines to reset cleanly without interrupting playback.
