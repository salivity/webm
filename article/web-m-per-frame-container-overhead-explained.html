WebM Per-Frame Container Overhead Explained

In a typical WebM file, the exact container-level overhead per frame ranges between 6 and 8 bytes when using standard SimpleBlock structures. WebM is a restricted subset of the Matroska (MKV) format based on Extensible Binary Meta Language (EBML). Because WebM eliminates unnecessary metadata layers and streamlines packet encapsulation, nearly all per-frame overhead is restricted to a compact binary header preceding the raw media payload.

The Anatomy of a WebM Frame (SimpleBlock)

In modern WebM streams (containing VP8, VP9, AV1, Opus, or Vorbis), individual media frames are packaged within a SimpleBlock EBML element. A SimpleBlock combines packet identification, timing, and frame flags into a single continuous header.

Here is the exact byte-by-byte breakdown of the overhead before the raw compressed frame data:

  1. Element ID (1 byte):

    • The EBML ID for SimpleBlock is 0xA3. This consumes exactly 1 byte.

  2. Data Size / Length Descriptor (1 to 3 bytes):

    • The size of the payload is encoded as a variable-length integer (EBML VINT).
    • 1 byte: Frame size \(\le\) 126 bytes (rare, occasional small audio frames).
    • 2 bytes: Frame size between 127 bytes and 16,382 bytes (common for audio and small 1080p/720p delta video frames).
    • 3 bytes: Frame size between 16,383 bytes and 2,097,150 bytes (typical for most high-bitrate video frames and 4K I-frames).

  3. Track Number (1 byte):

    • Stored as an EBML VINT. WebM files typically contain only two tracks (Track 1 for Video, Track 2 for Audio), meaning this value fits into 1 byte (e.g., 0x81 or 0x82).

  4. Relative Timecode (2 bytes):

    • A signed 16-bit integer representing the frame's presentation timestamp relative to the parent Cluster timecode. This field is fixed at 2 bytes.

  5. Flags (1 byte):

    • An 8-bit field containing frame-level metadata (Keyframe status, Invisible/Alt-ref flag, Discardable flag, and EBML Lacing mode). This field is fixed at 1 byte.

Exact Per-Frame Overhead Calculation

Summing these individual components yields the total byte overhead for an isolated frame:

\[\text{Overhead} = \text{Element ID (1B)} + \text{Size VINT (1–3B)} + \text{Track Number (1B)} + \text{Timecode (2B)} + \text{Flags (1B)}\]

  • Small Video Frames (< 16 KB) & Typical Audio Frames: \[1 + 2 + 1 + 2 + 1 = \mathbf{7\text{ bytes}}\]
  • Large Video Frames (16 KB to 2 MB): \[1 + 3 + 1 + 2 + 1 = \mathbf{8\text{ bytes}}\]
  • Very Small Audio Frames (< 127 bytes): \[1 + 1 + 1 + 2 + 1 = \mathbf{6\text{ bytes}}\]

Amortized Overhead: Clusters and BlockGroups

While SimpleBlock represents the direct per-frame encapsulation cost, two other structural elements can slightly alter the effective average overhead:

1. Cluster Overhead (Amortized: ~0.2 to 0.5 bytes/frame)

WebM frames are grouped inside Cluster elements, usually generated at every keyframe interval (1 to 5 seconds). A cluster header contains:

  • Cluster ID (0x1F43B675): 4 bytes
  • Cluster Size VINT: 2 to 8 bytes
  • Cluster Timestamp Element: 4 to 10 bytes

A standard Cluster header totals 10 to 22 bytes. When distributed across 30 to 150 frames within that cluster, it adds less than 0.5 bytes of amortized overhead per frame.

2. BlockGroup Structure (Infrequent: 11 to 14 bytes/frame)

If a frame requires explicit duration signaling or precise reference block tracking (common in older encoders, but discouraged in optimized WebM), a BlockGroup container is used instead of a SimpleBlock. This wraps a Block element inside a parent EBML structure, adding roughly 4 to 6 additional bytes, raising per-frame overhead to 11–14 bytes.
