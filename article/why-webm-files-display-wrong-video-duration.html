Why WebM Files Display Wrong Video Duration

WebM files frequently display incorrect, missing, or infinite video durations across various media players and web browsers due to missing header metadata, live-recording container limitations, and absent index cues. This issue commonly stems from how the container format handles timecodes during encoding, particularly during browser-based recordings. This article explains the technical causes of inaccurate WebM duration metadata and provides straightforward solutions to repair affected files.

Missing Duration Element in the EBML Header

WebM is a restricted subset of the Matroska (MKV) container format, which relies on Extensible Binary Meta Language (EBML). In a properly structured WebM file, the Segment Information element contains an explicit Duration tag that tells media players the exact length of the stream.

When encoders generate a WebM file, this metadata is typically placed near the beginning of the file. If an encoder cannot determine the length beforehand and fails to write this value after encoding finishes, the duration field remains blank, set to zero, or marked as unknown. When media players encounter this, they often default to displaying an infinite loop icon, a duration of 00:00, or an estimated duration that changes dynamically during playback.

The MediaRecorder API and Live Streaming

A major source of broken WebM durations is the browser-based MediaRecorder API used in modern web applications:

  • Real-time Chunking: When recording video in a browser (e.g., from a webcam or screen share), the browser writes WebM data in sequential chunks without knowing when the user will stop recording.
  • Unpatched Headers: Because standard streaming containers cannot predict the final length, the initial header is sent without a duration value. Once recording stops, many implementations save the raw stream directly to disk without reopening the file to patch the missing header duration.

Lack of Seek Indexes (Cues)

Matroska and WebM files utilize a Cues element, which acts as a seek table indexing keyframes and their respective timestamps.

When a media player opens a video file, it reads the Cues to determine both the end timestamp and the overall timeline. If a WebM file lacks this index:

  1. The player cannot seek forward accurately without reading the entire file sequentially.
  2. The player must guess the duration based on bitrate calculations, which are notoriously inaccurate for Variable Bitrate (VBR) files.

Truncated or Incomplete Downloads

If a WebM file download or transfer is interrupted, the end-of-file markers and closing tags will be missing. Media players will attempt to parse the partial file using timestamp packets (SimpleBlocks), but the file's overall metadata container remains broken, resulting in inaccurate progress bars and mismatched total time indicators.

How to Fix Incorrect WebM Duration Metadata

Fixing inaccurate WebM metadata does not require re-encoding the video or audio streams. Instead, remuxing the file will rewrite the EBML header and generate a proper duration and seek table.

Using FFmpeg

Run the following command to copy the audio and video streams into a freshly indexed WebM container:

ffmpeg -i input.webm -c copy output.webm

FFmpeg reads through the existing packets, calculates the correct total duration, writes the missing Duration tag to the header, and generates the necessary Cues element.

Using MKVToolNix

Remuxing the file through mkvmerge recalculates the container metadata automatically:

mkvmerge -o output.webm input.webm

For web applications creating WebM files on the fly, developers can integrate tools such as ts-ebml or fix-webm-duration into their JavaScript pipelines to inject the correct duration metadata into the recorded blob before saving or serving the file.
