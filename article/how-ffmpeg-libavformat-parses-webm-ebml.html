How FFmpeg Libavformat Parses WebM EBML

This article provides an overview of how FFmpeg’s libavformat library demuxes WebM media files by interpreting their underlying Extensible Binary Meta Language (EBML) architecture. It explores the shared relationship between Matroska and WebM within FFmpeg's codebase, examines the declarative syntax mapping tables used in matroskadec.c, details the variable-length integer (VINT) decoding mechanism, and explains how hierarchical EBML elements are transformed into standard internal primitives such as streams, packets, and codec parameters.

The Unified WebM and Matroska Demuxer

WebM is a constrained profile of the Matroska container format designed specifically for the web. Because WebM enforces Matroska’s underlying binary structure while restricting supported codecs primarily to VP8, VP9, AV1, Vorbis, and Opus, FFmpeg does not maintain an independent parsing engine for WebM. Instead, WebM files are routed directly through the unified Matroska demuxer implemented in libavformat/matroskadec.c.

When FFmpeg probes an incoming stream, it scans the file signature for the EBML header. If the EBML DocType tag contains webm, the demuxer registers the stream under the Matroska/WebM parser context while enforcing standard WebM-specific constraints during demuxing.

Declarative Parsing with EbmlSyntax

Rather than using complex procedural state machines to parse every individual element, libavformat employs a declarative, table-driven approach. The core of this mechanism is the EbmlSyntax structure.

typedef struct EbmlSyntax {
    uint32_t id;
    int type;
    size_t offset;
    union {
        uint64_t u;
        double   f;
        const char *s;
        const struct EbmlSyntax *n;
    } def;
} EbmlSyntax;

Each EbmlSyntax definition links an EBML Element ID (a variable-length hexadecimal identifier) to a designated C data type (such as integers, floats, strings, binary data, or nested master elements) and an offset within internal demuxer structs like MatroskaDemuxContext or MatroskaTrack.

FFmpeg defines hierarchical arrays of these syntax descriptors:

  • Header Elements: Tables define root-level metadata like EBMLVersion and DocType.
  • Segment Elements: Define Level 1 containers such as Info, Tracks, Cues, and Cluster.
  • Track Definitions: Define properties like TrackNumber, TrackType, CodecID, and default durations.
  • Master/Nested Elements: Use the EBML_NEST type to point recursively to sub-tables, directly mirroring the nested tree structure of the EBML file format.

Decoding Variable-Length Integers (VINT)

All EBML elements are serialized in a Type-Length-Value (TLV) format using variable-length integers (VINTs). The FFmpeg demuxer reads the raw byte stream sequentially using helper routines like ebml_read_num():

  1. Element ID Resolution: The parser reads the leading byte to count the number of consecutive zero bits preceding the first set bit. This determines the total byte length (between 1 and 4 bytes) of the Element ID.
  2. Element Length Calculation: The parser immediately reads the subsequent VINT to determine the payload size of the element. A length filled with binary ones indicates an unknown length, which is standard for streaming WebM clusters.
  3. Lookup and Deserialization: The demuxer takes the decoded Element ID and performs a lookup across the current EbmlSyntax table.

If the ID is found, ebml_parse_elem() reads the payload according to the defined type and writes the value directly into the corresponding memory offset of the demuxer's state context. If an ID is unrecognized, FFmpeg uses the parsed length to seek past the unknown element, ensuring backward and forward format compatibility.

Traversing Hierarchical EBML Elements

The WebM file structure maps to libavformat context structs through top-down recursive traversal:

  • EBML Header: Identifies protocol parameters and verifies that the file conforms to the webm specification.
  • Segment / Info: Extracts the container-level timescale (TimestampScale), application strings, and overall media duration.
  • Segment / Tracks: Parses individual track configurations. When an EBML_NEST containing track entries is encountered, the demuxer dynamically allocates a MatroskaTrack instance and populates video dimensions, pixel aspect ratios, audio sample rates, and channel layouts.
  • Segment / Cues: Parses random access indexes into the MatroskaIndex table to enable efficient seeking.
  • Segment / Cluster: Encapsulates the actual media payloads. Within each cluster, Timecode (timestamp) and SimpleBlock or BlockGroup elements are extracted.

Mapping EBML Payloads to FFmpeg Primitives

Once the metadata hierarchy is resolved, libavformat maps the EBML tree into standard FFmpeg abstractions:

  1. AVStream Creation: Each valid entry parsed from the Tracks element spawns a new AVStream attached to the AVFormatContext. The WebM CodecID (such as V_VP9 or A_OPUS) is translated to an FFmpeg AVCodecID (e.g., AV_CODEC_ID_VP9, AV_CODEC_ID_OPUS) and stored in AVStream->codecpar.
  2. Codec Private Data Extraction: Any CodecPrivate EBML binary element is copied into AVStream->codecpar->extradata, providing codec-specific initialization headers needed by downstream decoders.
  3. AVPacket Generation: When processing SimpleBlock structures within Clusters, the demuxer skips past the track number and relative timestamp flags, calculates the absolute presentation timestamp (PTS) by combining the Cluster timecode and the block's relative timecode, and packages the raw frame data into an AVPacket.

Through this table-driven mapping system, libavformat decouples low-level EBML binary parsing from high-level media stream handling, ensuring efficient and memory-safe WebM ingestion.
