WebM MSE: How Media Segments Signal Timestamp Offsets

This article explores how WebM media segments communicate timestamp offsets within Media Source Extensions (MSE) implementations. In WebM-based MSE streaming, presentation timing relies on a combination of container-level metadata defined in Matroska/EBML structures—such as TimecodeScale, Cluster base timecodes, and relative block offsets—working in tandem with the browser's SourceBuffer timestamp management properties. Understanding this interaction clarifies how MSE parsers decode, align, and seamlessly append segmented audio and video streams.

The Matroska/EBML Timing Hierarchy

WebM is a subset of the Matroska (MKV) container format, which utilizes Extensible Binary Meta Language (EBML). Timing information in WebM is structured hierarchically across initialization segments and media segments.

  1. Initialization Segment (Info and TimecodeScale):
    The initialization segment contains the Segment Information (Info) element, which defines the global TimecodeScale (nanoseconds per timecode tick). By default, this value is 1,000,000 nanoseconds (1 millisecond). All subsequent timecode values in media segments are multiplied by this scale to convert them into absolute time.

  2. Media Segment Level (Cluster Timecode):
    A WebM media segment consists of one or more Cluster elements. Each Cluster contains an absolute Timecode (or Timestamp in newer EBML specifications) element. This value serves as the base presentation time for all media samples contained within that cluster.

  3. Sample Level (SimpleBlock and BlockGroup Offsets):
    Individual audio and video frames are stored within SimpleBlock or BlockGroup elements inside the cluster. Instead of storing absolute timestamps, each block stores a signed 16-bit integer representing a relative time offset from the parent Cluster timecode.

The resulting stream presentation timestamp (PTS) within the container is calculated as: \[\text{Container PTS} = (\text{Cluster Timecode} + \text{Block Timecode Offset}) \times \text{TimecodeScale}\]

How the MSE SourceBuffer Applies Timestamp Offsets

When WebM media segments are appended to an MSE SourceBuffer, the browser's demuxer reads the container timestamps and maps them to the media timeline according to the SourceBuffer configuration.

1. The timestampOffset Property

The SourceBuffer.timestampOffset attribute in the JavaScript MSE API allows developers to adjust the presentation timeline manually. When a segment is appended, the browser applies this offset to the timestamps parsed from the WebM container:

\[\text{Final Presentation Time} = \text{Container PTS} + \text{SourceBuffer.timestampOffset}\]

This mechanism allows separate WebM media segments—which may internally start at time 0 or contain discontinuous cluster timecodes—to be placed contiguously on the playback timeline.

2. Append Modes: segments vs. sequence

The MSE pipeline handles container timestamps differently depending on SourceBuffer.mode:

  • segments Mode (Default):
    The browser uses the WebM Cluster timecodes directly, adjusted by timestampOffset. Media segments with specific internal timecodes are placed at those exact positions on the timeline. If the segment timestamps do not align with previously appended data, gaps or overlaps may occur.

  • sequence Mode:
    The browser disregards the absolute values of the internal Cluster timecodes for timeline positioning. Instead, it automatically updates timestampOffset to match the end timestamp of the previously appended segment. The WebM cluster timestamps are only used to preserve the relative duration and pacing of frames within that specific segment.

Summary of the Offset Communication Flow

  1. The Initialization Segment sets the time unit resolution via TimecodeScale.
  2. Each Media Segment (Cluster) declares a base timestamp via its internal Timecode element.
  3. Individual Blocks provide relative sub-offsets to determine specific frame presentation times.
  4. The MSE Implementation extracts these container timestamps and applies the SourceBuffer.timestampOffset to position the decoded frames on the playback timeline.
