Strip Unused WebM Audio Tracks with Edge Workers

This article explains how edge workers dynamically strip unneeded audio tracks from WebM video files to reduce egress bandwidth and lower latency. By intercepting client requests at the network edge, edge computing runtimes inspect the WebM container's binary structure, discard non-requested audio streams—such as secondary language tracks or multi-channel surround sound—and stream only the requested content directly to the user.

The Bandwidth Problem of Multi-Track WebM

Modern web video often packages multiple localized audio tracks (such as English, Spanish, or commentary tracks) into a single container format. In standard delivery architectures, a browser fetching a WebM file downloads every embedded track within the file's data clusters, even though it only plays one at a time. This results in significant bandwidth waste, slower start times, and unnecessary egress costs for content providers.

Understanding the WebM Container Structure

WebM is built on EBML (Extensible Binary Meta Language), a hierarchical binary format similar to XML. A WebM file contains distinct elements:

  1. EBML Header: Identifies the file type and parser specifications.
  2. Segment: The root container holding all media data.
  3. Tracks Element: Metadata defining each video, audio, and subtitle track, including its unique Track Number, Codec ID, and Language tag.
  4. Cluster Elements: Time-synced blocks of media data containing SimpleBlock or BlockGroup structures tagged with their corresponding Track Number.

Interception and Track Selection at the Edge

When a client requests a video, an edge worker (running on runtimes such as Cloudflare Workers, Fastly Compute, or AWS CloudFront Functions) intercepts the HTTP request.

The worker determines the desired audio track using:

  • Request query parameters (e.g., ?audio=en)
  • The client's Accept-Language header
  • Custom player headers or client hints

If the requested configuration matches an optimized profile, the worker fetches the source file from the origin or edge cache and routes the incoming byte stream through a transformation pipeline.

Dynamic Stream Parsing and Demuxing

Edge workers have strict memory and execution time limits, meaning they cannot buffer entire video files in memory. Instead, they use lightweight streaming parsers—typically written in Rust and compiled to WebAssembly (Wasm) for high-performance binary manipulation.

The parsing process follows these steps:

  1. Header Rewriting: The worker reads the Tracks master element in the WebM header. It removes the TrackEntry definitions for the unwanted audio tracks, updates the total track count, and recalculates the element size before passing the bytes to the response stream.
  2. Cluster Filtering: As the media payload streams through subsequent Cluster elements, the worker inspects each SimpleBlock or BlockGroup. Each block begins with a variable-length integer indicating its Track Number.
  3. Byte Discarding: If the block belongs to an excluded audio track, the worker drops those bytes from the output stream entirely. If it belongs to the video or the chosen audio track, the bytes are passed through unchanged.
  4. Cluster Size Adjustment: If the WebM clusters use explicit size headers rather than unknown-length descriptors, the worker dynamically adjusts the cluster size bytes to reflect the discarded audio payloads.

Edge Streaming and Caching Strategies

By utilizing edge streams (such as the Web standard TransformStream), the worker begins sending data to the client immediately after parsing the initial header, maintaining an optimal Time to First Byte (TTFB).

To prevent repetitive processing of popular assets, edge architectures store the transformed responses in the edge cache. By modifying the cache key to include the selected language or audio layout (e.g., video-12345.webm?audio=es), subsequent requests for the same track configuration are served directly from the edge cache without re-invoking the Wasm parser.
