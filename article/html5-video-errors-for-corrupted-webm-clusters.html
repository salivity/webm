HTML5 Video Errors for Corrupted WebM Clusters

When an HTML5 <video> element encounters a corrupted WebM cluster during playback, it halts media processing and dispatches a standard DOM error event. Because a corrupted cluster represents an inability to parse or decode valid container structures (EBML) or media frames, the media engine flags this state by setting the element's video.error attribute to a MediaError object with the code MEDIA_ERR_DECODE (numeric value 3). Understanding how this error surfaces, along with browser-specific diagnostic messages, enables developers to detect playback failures and implement proper recovery mechanisms.

The Primary Error Type: MEDIA_ERR_DECODE

The HTML5 media specification defines four standard error codes on the MediaError interface:

  1. MEDIA_ERR_ABORTED (Code 1): Playback was aborted by the user agent.
  2. MEDIA_ERR_NETWORK (Code 2): A network error caused playback to fail.
  3. MEDIA_ERR_DECODE (Code 3): An error occurred while decoding the media resource after it was determined to be usable.
  4. MEDIA_ERR_SRC_NOT_SUPPORTED (Code 4): The media format or MIME type is not supported.

A WebM cluster contains the actual timing and media blocks (such as SimpleBlock or BlockGroup elements). If the cluster header, size descriptors, or inner payloads contain corrupted bytes, the browser's demuxer can no longer parse the Matroska/WebM structure or feed valid packets to the audio/video decoder. This failure directly triggers:

video.error.code === MediaError.MEDIA_ERR_DECODE; // Evaluates to true (numeric code 3)

Extended Error Details (MediaError.message)

While the W3C specification strictly categorizes container and stream decode failures under MEDIA_ERR_DECODE, modern browsers provide detailed strings via video.error.message to specify the exact parsing breakdown:

  • Chromium-based Browsers (Chrome, Edge): The pipeline outputs demuxer-specific errors, often represented as DEMUXER_ERROR_COULD_NOT_PARSE or CHUNK_DEMUXER_ERROR_APPEND_FAILED. In the case of severe EBML header corruption inside a cluster, Chromium logs pipeline errors such as PIPELINE_ERROR_DECODE with a subtext pointing to invalid WebM/Matroska parsing.
  • Mozilla Firefox: Firefox surfaces internal decode diagnostics, often referencing NS_ERROR_DOM_MEDIA_DECODE_ERR or specific Gecko Media Plugin (GMP) decoding faults pointing to corrupted container frames.
  • Safari: Safari relies on underlying AVFoundation and CoreMedia frameworks (when WebM playback is supported), exposing decode failure descriptions within the console and setting the error code to 3.

Media Source Extensions (MSE) Behavior

If the corrupted WebM is being delivered via Media Source Extensions (MSE) rather than a direct src URL:

  1. Appending the corrupted cluster to a SourceBuffer triggers an error event directly on the SourceBuffer object.
  2. The sourceBuffer.appendBuffer() operation fails, throwing a DecodeError DOMException.
  3. The parent MediaSource.readyState transitions to ended.
  4. The parent <video> element subsequently fires its own error event, once again exposing MediaError.MEDIA_ERR_DECODE.

Detecting the Error in JavaScript

To programmatically detect and inspect a corrupted WebM cluster failure, listen for the error event on the media element:

const video = document.querySelector('video');

video.addEventListener('error', (event) => {
  const mediaError = video.error;

  if (mediaError && mediaError.code === MediaError.MEDIA_ERR_DECODE) {
    console.error('Decoding failed: Corrupted WebM cluster or bitstream.');
    console.error(`Diagnostic details: ${mediaError.message}`);
  }
});

When this error occurs, playback cannot resume automatically. The application must handle the failure by reloading the stream, requesting an alternative bitrate/source, or skipping past the corrupted cluster timestamp.
