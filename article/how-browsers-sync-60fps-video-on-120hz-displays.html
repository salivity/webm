How Browsers Sync 60fps Video on 120Hz Displays

Modern web browsers achieve seamless 120Hz display synchronization when playing 60fps WebM video assets by utilizing integer frame cadence, hardware-accelerated decoding pipelines, and synchronized compositor scheduling. Because 120Hz is an exact multiple of 60fps, browsers employ a 2:2 pulldown cadence, displaying every decoded frame for precisely two refresh cycles. This eliminates frame judder while leveraging platform-level display APIs to prevent visual tearing and minimize presentation latency.

The Integer Ratio: 2:2 Cadence

The primary advantage of displaying 60fps content on a 120Hz monitor is mathematical simplicity. Unlike displaying 24fps film content on a 60Hz display—which requires an asymmetrical 3:2 pulldown that introduces perceptible judder—a 120Hz display updates twice as fast as a 60fps video stream.

Browsers map each 16.67ms video frame directly to two 8.33ms display refresh intervals. As long as frames are delivered on schedule, the browser simply doubles each frame across two consecutive vertical synchronization (V-Sync) intervals, resulting in fluid, judder-free playback.

Video Decoding and Presentation Timestamps

When playing a WebM asset—typically containing VP8, VP9, or AV1 video streams—the browser executes the following sequence:

  1. Demuxing: The browser extracts video packets and their corresponding Presentation Timestamps (PTS) from the WebM container.
  2. Hardware Decoding: The compressed bitstream is fed into dedicated GPU hardware decoders (such as NVDEC, Intel Quick Sync, or Apple VideoToolbox) via the operating system's media framework.
  3. Frame Queuing: Decoded raw surfaces (typically YUV420) are placed into a video frame queue alongside their target PTS metadata.

Compositor Decoupling and Frame Scheduling

Modern browsers (such as Chromium-based engines, Gecko, and WebKit) decouple media decoding from rendering using dedicated threads.

Chromium, for example, utilizes the VideoFrameSubmitter and the cc (Chrome Compositor) system. The compositor receives hardware V-Sync pulses generated by the operating system at 120Hz. For every tick:

  • The video frame scheduler examines the presentation timestamps of frames in the decoded queue against the target display time.
  • If a frame's ideal presentation window spans two 120Hz intervals, the compositor retains the current texture in the GPU swap chain for both display intervals.
  • The compositor avoids performing unnecessary pixel re-renders when a video frame is duplicated, merely instructing the GPU to present the existing surface again during the second V-Sync phase.

Direct Scanout and OS-Level Swap Chains

To minimize power consumption and latency, browsers rely on zero-copy video presentation architectures:

  • Windows: Browsers use DirectComposition and DXGI Swap Chains (DXGI_SWAP_EFFECT_FLIP_DISCARD). The video frame is promoted to an independent hardware overlay plane, allowing the Desktop Window Manager (DWM) to scan it directly to the display without recompiling the entire webpage DOM.
  • macOS: Browsers pass decoded frames into CALayer hierarchies managed by CoreAnimation, which dynamically adjusts layer presentation to match ProMotion (120Hz) displays.
  • Linux: Browsers leverage Wayland presentation-time protocols or DRM/KMS interfaces via EGL to schedule buffer flips aligned directly to display refresh boundaries.

Clock Drift and Drop/Repeat Handling

Audio clocks serve as the ultimate master clock for web media playback. Because the system audio clock and the display panel’s refresh clock can drift apart slightly over time, browsers employ frame-scheduling algorithms to compensate:

  • Minor Timing Drift: The browser shifts frame presentation thresholds fractionally, absorbing phase differences within the double-refresh window.
  • Decoder Lag: If the decoder falls behind, the browser skips a stale frame and presents the newer frame to restore synchronization with the audio clock.
  • Buffer Underflow: If a frame is missing entirely, the compositor holds the previous frame for an extra V-Sync cycle (3:2 exception) until the pipeline catches up, returning immediately to the stable 2:2 cadence.
