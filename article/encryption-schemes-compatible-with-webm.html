Encryption Schemes Compatible with WebM

This article provides an overview of the encryption schemes supported by the WebM media container format, focusing on how Common Encryption (CENC) principles, AES-128 encryption, and modern Digital Rights Management (DRM) systems operate within WebM streams.

The WebM Encryption Standard: AES-128-CTR

WebM, derived from the Matroska (MKV) container, relies primarily on AES-128 in Counter (CTR) mode for content protection. Defined by the official WebM Encryption Specification, this implementation encrypts video (such as VP8, VP9, and AV1) and audio (such as Opus and Vorbis) sample payloads while preserving unencrypted container headers to allow media parsers to navigate the stream.

In this model:

  • Cipher: AES with 128-bit keys.
  • Mode: CTR (Counter Mode), allowing random access and parallel decryption without ciphertext expansion.
  • Initialization Vectors (IVs): Typically 64-bit or 128-bit counter values assigned per block or frame to ensure cryptographic safety.

Compatibility with Common Encryption (CENC)

Common Encryption (ISO/IEC 23001-7) was originally developed for the ISO Base Media File Format (ISOBMFF / MP4). While WebM does not use the MP4 pssh (Protection System Specific Header) box directly inside its container elements, it implements a structurally aligned encryption scheme equivalent to the standard cenc protection scheme (AES-CTR mode).

Key Metadata Mapping

WebM handles CENC-equivalent metadata using Matroska ContentEncryption elements:

  • ContentEncAlgo: Set to 4 (AES).
  • ContentCipherMode: Set to 1 (CTR mode).
  • ContentEncKeyID: Contains the 16-byte Key ID (KID) identifying the decryption key required by the DRM license.
  • ContentEncAESSettings: Configures specific AES handling flags.

This design ensures that streaming protocols like Dynamic Adaptive Streaming over HTTP (DASH) can deliver WebM content protected by the same key-management workflows used for CENC-protected MP4 files.

Subsample Encryption

Similar to CENC in MP4, WebM supports subsample encryption. Instead of encrypting an entire video frame or audio packet, selective bytes (such as slice headers or specific structural metadata) can be left in cleartext. This allows hardware decoders and media pipelines to parse container and codec structures without needing to route non-payload data through secure decryption modules.

Supported DRM Systems and Key Management

WebM's AES-CTR encryption is compatible with major content protection technologies:

  • Google Widevine (Modular): The most common commercial DRM used with encrypted WebM across Chromium-based browsers, Android, and smart TVs via Encrypted Media Extensions (EME).
  • ClearKey: The W3C EME standard key system for testing and basic unencrypted key exchange, fully supported with WebM AES-CTR streams.

Limitations with CBC-Based Schemes

Unlike modern ISOBMFF implementations that frequently use the cbcs protection scheme (AES-CBC with pattern protection, required by Apple FairPlay), WebM does not natively support or standardly implement CBC-based pattern encryption. Systems requiring cbcs encryption typically deploy fragmented MP4 (fMP4) containers rather than WebM.
