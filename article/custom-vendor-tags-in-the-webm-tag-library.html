Custom Vendor Tags in the WebM Tag Library

The WebM container format, derived from the Matroska (MKV) specification, utilizes an Extensible Binary Meta Language (EBML) structure to store multimedia data and metadata. Custom vendor-specific metadata tags are integrated by nesting custom SimpleTag elements within the standard WebM Tags infrastructure. This article outlines the exact EBML hierarchy, element requirements, naming conventions, and structural methods used to define and store proprietary or vendor-specific metadata in WebM files.

The WebM Tag Hierarchy

WebM organizes metadata inside a top-level Tags master element located within the root Segment. The metadata tree follows this standardized EBML structure:

Segment
 └── Tags
      └── Tag
           ├── Targets
           │    └── TargetTypeValue (optional)
           └── SimpleTag
                ├── TagName
                ├── TagString (or TagBinary)
                ├── TagLanguage (optional)
                ├── TagDefault (optional)
                └── SimpleTag (nested, optional)

Key Elements Explained

  • Tags (ID: 0x1254C367): The master container holding one or more Tag elements.
  • Tag (ID: 0x7373): Contains metadata targeting a specific level of the file (such as a track, chapter, or the whole file) along with the associated metadata values.
  • Targets (ID: 0x63C0): Defines the scope of the tag via TargetTypeValue (e.g., 50 for file/movie, 30 for track) or target UID references (TargetTrackUID). If omitted, the tag applies globally to the entire media file.
  • SimpleTag (ID: 0x67C8): The core key-value element where metadata is declared.

Structuring Vendor-Specific Data with SimpleTag

To store custom vendor data, developers define custom names inside the TagName element rather than using generic Matroska tags (like TITLE or ARTIST).

1. TagName (ID: 0x45A3)

Contains the UTF-8 string representing the key. For vendor-specific metadata, it is standard practice to use a vendor prefix or namespace convention to prevent collisions with official Matroska/WebM tags and third-party tools.

  • Examples: COM.VENDOR.ASSET_ID, X_VENDOR_ENCODER_SETTINGS, VENDOR_CUSTOM_FLAG

2. Value Representation (TagString or TagBinary)

  • TagString (ID: 0x4487): A UTF-8 formatted string containing plain text, JSON, XML, or base64-encoded strings.
  • TagBinary (ID: 0x4485): Raw binary data for proprietary binary blobs, serialized schemas, or encryption fingerprints.

3. Localization and Defaults

  • TagLanguage (ID: 0x447A): The language of the tag value using the standard ISO 639-2 language code (or BCP 47 in modern implementations). Defaults to und (undetermined).
  • TagDefault (ID: 0x4484): A boolean indicating if this tag instance is the default when multiple language instances of the same TagName are present.

Nested Vendor Structures

WebM allows SimpleTag elements to be nested within other SimpleTag elements. This enables complex, object-like hierarchical data structures.

<Tags>
  <Tag>
    <Targets>
      <TargetTypeValue>50</TargetTypeValue> <!-- Entire File Scope -->
    </Targets>
    <SimpleTag>
      <TagName>VENDOR_PROPERTIES</TagName>
      <!-- Child SimpleTag 1 -->
      <SimpleTag>
        <TagName>DEVICE_ID</TagName>
        <TagString>CAM-UNIT-8842</TagString>
      </SimpleTag>
      <!-- Child SimpleTag 2 -->
      <SimpleTag>
        <TagName>CALIBRATION_MATRIX</TagName>
        <TagString>0.99,0.01,0.00;0.00,1.00,0.00</TagString>
      </SimpleTag>
    </SimpleTag>
  </Tag>
</Tags>

Best Practices for Custom Tags

  1. Prefix Usage: Always prepend vendor names or an X_ identifier to custom tags to prevent conflicts if future official Matroska tag specifications introduce new keys.
  2. Character Encoding: TagName and TagString values must always be valid UTF-8. Non-UTF-8 character sets can cause parser failures.
  3. Size Constraints: Keep custom metadata lightweight. Extremely large metadata blocks placed before media clusters can delay initial playback buffering in streaming environments.
