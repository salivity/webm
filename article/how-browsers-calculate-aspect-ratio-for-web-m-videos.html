How Browsers Calculate Aspect-Ratio for WebM Videos

This article examines how modern browser layout engines compute the CSS aspect-ratio property for dynamically loaded WebM video files. It outlines the interaction between the CSS box model, the parsing of WebM container metadata, and the layout recalculation passes that occur when a video stream's intrinsic dimensions become available to engines like Blink, Gecko, and WebKit.

Initial Layout Sizing and the Default Aspect Ratio

When a <video> element is dynamically injected into the Document Object Model (DOM) to load a WebM resource, the browser's layout engine must establish dimensions before the underlying network request resolves. If the element lacks explicit width, height, or CSS aspect-ratio properties, the engine assigns an intrinsic size of 300 CSS pixels wide by 150 CSS pixels high, yielding a default 2:1 ratio per the HTML and CSS specifications.

If an author declares an explicit CSS aspect-ratio (for example, aspect-ratio: 16 / 9), the layout engine ignores the 300x150 fallback. Instead, the engine creates a layout box whose inline and block axes are constrained by that ratio relative to whichever dimension is determined first by its parent formatting context.

Parsing WebM Container Metadata

WebM files are built upon an EBML (Extensible Binary Meta Language) container structure, which is a subset of Matroska. To determine a video's actual dimensions, the browser’s media pipeline streams the file until it reads the EBML Header and reaches the Segment's Tracks element.

Inside the TrackEntry with a TrackType of video, the demuxer extracts two critical pairs of integer values:

  • PixelWidth and PixelHeight: The raw pixel dimensions of the encoded video frames.
  • DisplayWidth and DisplayHeight: Optional parameters defining the intended rendering dimensions when dealing with non-square pixels (anamorphic video).

Once the demuxer reads these elements, the media pipeline calculates the intrinsic aspect ratio as:

\[\text{Intrinsic Ratio} = \frac{\text{DisplayWidth}}{\text{DisplayHeight}} \quad \text{(or } \frac{\text{PixelWidth}}{\text{PixelHeight}} \text{ if display values are absent)}\]

This value is passed from the media decoding thread to the main browser thread via the layout engine’s media element representation (such as Blink's HTMLVideoElement and LayoutVideo).

Resolution of the CSS aspect-ratio Property

Once the intrinsic dimensions are communicated to the main thread, the layout engine resolves the computed value of the CSS aspect-ratio according to its declared syntax:

  1. Explicit Ratio (aspect-ratio: <ratio>): If a fixed ratio is defined (such as 16 / 9), the layout engine maintains this ratio regardless of what the WebM metadata reports. The video content itself is fitted into this box according to the object-fit property (defaulting to contain).
  2. Auto with Ratio (aspect-ratio: auto <ratio>): The engine uses the specified fallback <ratio> until the WebM metadata arrives. As soon as the DisplayWidth and DisplayHeight are parsed, the auto keyword takes precedence, and the layout engine replaces the fallback ratio with the intrinsic ratio extracted from the WebM header.
  3. Implicit Auto (aspect-ratio: auto): The engine initially uses the 300x150 ratio. Once metadata parsing exposes the video's actual dimensions, the intrinsic ratio replaces the default values.

Layout Invalidation and Reflow

When the media engine updates the intrinsic dimensions, the layout engine marks the video element's layout object as dirty. This triggers an asynchronous layout invalidation:

  • The engine evaluates whether the new intrinsic ratio changes the box’s computed dimensions. If the element's width is fixed (e.g., width: 100%) and its height relies on the aspect ratio, the height is recomputed as:

\[\text{Computed Height} = \frac{\text{Computed Width}}{\text{Aspect Ratio}}\]

  • If the computed box dimensions change, the layout engine performs a reflow (layout pass) on the element and any ancestor or sibling nodes affected by the change in flow.
  • The browser then dispatches the loadedmetadata event to JavaScript, while the compositor thread updates the rendering layer to prepare for rendering the first incoming decoded VP8, VP9, or AV1 video frame inside the newly calculated boundary.
