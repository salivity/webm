WebM SimpleBlock Header Binary Format

This article provides an exact breakdown of the binary structure of the SimpleBlock header in a WebM container. A SimpleBlock is an EBML element used to store raw encoded audio or video frames along with their associated metadata, such as track identification, relative timestamps, and keyframe indicators.

EBML Element Wrapper

Before reaching the internal payload of a SimpleBlock, the element is wrapped in standard EBML (Extensible Binary Meta Language) syntax:

  1. Element ID: 0xA3 (1 byte, encoded as an EBML Variable Size Integer).
  2. Element Data Size: 1 to 8 bytes (EBML VINT indicating the total byte length of the SimpleBlock payload).

SimpleBlock Payload Header Structure

The internal data inside a SimpleBlock begins with a mandatory header followed immediately by the raw media frame data (or optional lacing data). The minimum header length is 4 bytes (when Track Number is a 1-byte VINT).

+-------------------+-------------------+-------------------+-------------------+
|  Track Number     | Timecode (High)   | Timecode (Low)    | Flags             |
|  (EBML VINT: 1-8B)| (Signed Int16)    | (Signed Int16)    | (1 Byte Bitfield) |
+-------------------+-------------------+-------------------+-------------------+
| Optional Lacing Data (if lacing bits != 00)                                   |
+-------------------------------------------------------------------------------+
| Frame Data Payload...                                                         |
+-------------------------------------------------------------------------------+

1. Track Number (Variable Length: 1–8 Bytes)

  • Format: EBML Variable Size Integer (VINT).
  • Description: Identifies which track the frame belongs to. For Track 1, this is represented as a single byte: 0x81.

2. Timecode / Relative Timestamp (2 Bytes)

  • Format: Signed 16-bit integer, Big-Endian (int16_t).
  • Description: The presentation timestamp of the block relative to the Timestamp (or Timecode) of its parent Cluster. The actual time is calculated as: \[\text{Timestamp} = (\text{Cluster Timestamp} + \text{Block Timecode}) \times \text{TimestampScale}\]

3. Flags (1 Byte)

The 8-bit bitfield controls frame behavior and defines how the payload is parsed:

  • Bit 0 (MSB, 0x80) — Keyframe:
    • 1: Frame is a keyframe (independent frame).
    • 0: Frame is not a keyframe (inter-frame).
  • Bits 1–3 (0x70) — Reserved:
    • Must be set to 000.
  • Bit 4 (0x08) — Invisible:
    • 1: The frame is decoded to update the codec state but not displayed.
    • 0: The frame is displayed normally.
  • Bits 5–6 (0x06) — Lacing:
    • 00: No lacing (contains exactly one frame).
    • 01: Xiph lacing.
    • 10: Fixed-size lacing.
    • 11: EBML lacing.
  • Bit 7 (LSB, 0x01) — Discardable:
    • 1: The frame can be dropped without breaking the decoding of subsequent frames.
    • 0: The frame is required for reference.

4. Lacing Header (Optional: Variable Length)

If Bits 5–6 of the Flags byte are not 00, a lacing header immediately follows the Flags byte:

  • Frame Count (1 byte): Contains \(N - 1\), where \(N\) is the number of frames stored in the lace.
  • Frame Sizes: The byte sizes of individual frames encoded using the format specified by the lacing bits (e.g., EBML VINTs or Xiph byte sums).

Frame Data

The raw, encoded media frame (e.g., VP8, VP9, AV1, or Opus data) directly follows the Flags byte (if no lacing is used) or the Lacing Header (if lacing is present), extending for the remainder of the block's declared size.
