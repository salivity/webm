VP9 Intra-Only Frame Bitstream Characteristics

In the VP9 video coding standard, an intra-only frame that does not function as an Instantaneous Decoder Refresh (IDR) frame allows full intra-prediction coding while maintaining existing reference frame buffers. Unlike standard keyframes that reset the decoder state to serve as random access points, these non-IDR intra frames enable high-efficiency compression and flexible reference management. This article examines the exact bitstream flags, uncompressed header fields, and WebM container-level attributes that define a VP9 intra-only, non-key frame.

The VP9 Frame Type Architecture

VP9 categorizes frames into two fundamental types at the bitstream level: KEY_FRAME and INTER_FRAME (non-key frame).

  • KEY_FRAME (frame_type = 0): Operates as a traditional IDR frame. It is entirely intra-coded, completely resets decoder probability models, and overwrites or invalidates all eight internal reference frame buffers.
  • INTER_FRAME (frame_type = 1): Typically encodes inter-predicted data using temporal references. However, the VP9 specification allows an inter frame to be signaled as exclusively intra-coded through a dedicated sub-flag.

An intra-only non-IDR frame is functionally an INTER_FRAME that borrows intra-coding tools without triggering the global buffer flush of a KEY_FRAME.

Uncompressed Header Syntax Elements

To identify a VP9 intra-only non-IDR frame within the bitstream, the uncompressed frame header must present a specific sequence of syntax elements:

  1. frame_marker (2 bits): Must equal 0b10 (2), confirming standard VP9 bitstream synchronization.
  2. profile_low_bit and profile_high_bit (1–3 bits): Designates the VP9 profile (0 through 3).
  3. show_existing_frame (1 bit): Must be 0. A value of 1 immediately displays a previously decoded buffer and bypasses the rest of the uncompressed header.
  4. frame_type (1 bit): Must be 1 (Non-Key Frame). Setting this to 0 would define a standard keyframe/IDR.
  5. show_frame (1 bit): Can be either 0 (an alternate reference frame) or 1 (displayed immediately).
  6. error_resilient_mode (1 bit): Can be 0 or 1.
  7. intra_only (1 bit): Must be 1.

Because frame_type is set to 1, the decoder parses the intra_only flag immediately following error_resilient_mode. When intra_only == 1, the decoder knows that the current frame contains zero motion vectors and uses intra prediction exclusively across all transform blocks, while retaining non-keyframe semantics.

Reference Buffer Management

The defining operational difference between an IDR keyframe and a non-IDR intra-only frame is reference buffer preservation:

  • refresh_frame_flags (8 bits): In an intra-only frame, this field explicitly specifies which of the eight decoder reference frame buffers are updated with the reconstructed data of the current frame.
  • Buffer Retention: Unlike a keyframe (which forces all reference slots to point to the newly decoded frame), an intra-only frame allows selective replacement. Reference slots that are not targeted by refresh_frame_flags remain untouched. Consequently, subsequent P-frames or B-frames can reference frames that appeared temporally prior to this intra-only frame, violating the definition of an IDR sync point.

Context and Probability Resets

In a VP9 keyframe, probability tables are unconditionally reset to default values. For an intra-only frame (frame_type == 1 and intra_only == 1), context adaptation is controlled by the reset_frame_context syntax element (2 bits):

  • 0 or 1: Do not reset, or reset only the context specified by frame_context_idx.
  • 2: Reset all contexts to default tables.
  • 3: Full reset.

Even if reset_frame_context specifies a full reset, the frame remains structurally a non-IDR frame due to the selective retention of the reference picture buffers.

WebM Container Mapping

At the WebM (Matroska) container level, video frames are stored inside SimpleBlock or BlockGroup elements.

Within a SimpleBlock:

  • Keyframe Flag (Bit 7 of the flags byte): Set to 0.

Because a VP9 intra-only non-key frame retains references across its boundary, it is not a clean random access point. Consequently, WebM demuxers and multiplexers mark the container-level keyframe bit as 0 to prevent video players from seeking directly to this frame without also decoding preceding reference dependencies.
