How Wikimedia Transcodes Videos into WebM

Wikimedia's video transcoding pipeline transforms diverse, user-uploaded video files into standardized, multi-resolution WebM streams to ensure open-access, web-compatible playback across all devices. Managed primarily by the TimedMediaHandler extension within MediaWiki, this automated system ingests source media, schedules encoding tasks through a distributed job queue, invokes optimized FFmpeg profiles for varying resolutions, and stores the resulting VP8/VP9 derivatives in an object storage cluster for seamless streaming via Wikimedia’s content delivery network.

1. Ingestion and Metadata Extraction

When a user uploads a video to Wikimedia Commons or Wikipedia, MediaWiki registers the file and triggers the TimedMediaHandler extension. The system first inspects the original file using tools like FFprobe to extract technical metadata, including codec details, aspect ratio, frame rate, audio channels, and native resolution. If the source file is in an uncompressed or high-bitrate format, this inspection determines which derivative resolutions need to be generated.

2. Derivative Scheduling and the Job Queue

Wikimedia avoids direct, synchronous encoding during upload to prevent server timeouts. Instead, TimedMediaHandler evaluates the native resolution and creates a set of target profiles. The system only schedules derivatives that are equal to or smaller than the original resolution to prevent upscaling.

Standard WebM derivative heights typically include:

  • Low-bandwidth profiles: 160p, 240p, 360p
  • Standard and High Definition profiles: 480p, 720p, 1080p, and higher (if supported by source)

Each resolution requirement is pushed as an independent background job to Wikimedia’s distributed JobQueue infrastructure (backed by Kafka and Redis), which distributes the tasks across dedicated transcode worker servers.

3. Encoding with FFmpeg

When a worker node picks up a transcode job, it runs FFmpeg with strict profile settings tailored for the open WebM container:

  • Video Encoding: The pipeline utilizes the libvpx or libvpx-vp9 video codecs. It applies multi-pass or constrained quality (CRF) encoding parameters to balance compression efficiency with processing time. The video is scaled down to the target height while maintaining the original aspect ratio.
  • Audio Encoding: Audio tracks are converted to Vorbis or Opus codecs, normalized, and synchronized with the video stream.
  • Open Standards Enforcement: To uphold Wikimedia's commitment to free culture, the WebM pipeline relies exclusively on royalty-free codecs, avoiding proprietary formats like H.264/H.265 in its primary open-source pipeline.

4. Storage, Verification, and Delivery

Once FFmpeg successfully completes a transcode:

  1. Verification: TimedMediaHandler validates that the output WebM file is non-empty, properly structured, and plays back without container errors.
  2. Storage: The output derivative is transferred to OpenStack Swift, Wikimedia’s distributed object storage system.
  3. Database Update: MediaWiki updates its database tables to map the original file ID to the newly available derivative URLs and dimensions.
  4. CDN Caching: The derivatives are cached at edge caching layers (Varnish/Traffic servers).

When a user views a video on Wikipedia, the front-end player (VideoJS/MwEmbed) reads the available WebM derivatives and dynamically selects or allows manual switching between resolutions based on the client's screen size and bandwidth.
