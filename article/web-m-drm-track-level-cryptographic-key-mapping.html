WebM DRM Track-Level Cryptographic Key Mapping

This article explains how track-level cryptographic keys are mapped when encapsulating DRM-protected WebM media. Encapsulating protected audio and video streams within the WebM container requires binding unique Key Identifiers (KIDs) to specific tracks using Matroska-based Extensible Binary Meta Language (EBML) elements. Understanding this mapping process is essential for implementing common encryption across diverse streaming platforms, ensuring that Content Decryption Modules (CDMs) can resolve the correct decryption keys for individual media streams.

The WebM Encryption Architecture

WebM inherits its container layout from Matroska, using structured EBML elements to define media parameters. When encrypting a WebM file, encryption metadata is split into two areas: track-level configuration stored in the container header, and sample-level initialization vectors (IVs) stored alongside individual media blocks. Track-level key mapping establishes which media track corresponds to which cryptographic key before playback begins.

EBML Key Mapping Structure

Key mapping occurs inside the Tracks master element. Each media stream—such as an audio track or a video track—is defined by a individual TrackEntry. To declare encryption for that specific stream, the container includes the ContentEncodings element directly within the TrackEntry.

The hierarchy functions as follows:

  • TrackEntry: Contains all metadata for a specific media track.
    • ContentEncodings: A master element containing one or more encoding configurations.
      • ContentEncoding: Defines a single transformation applied to the track (such as compression or encryption).
        • ContentEncodingOrder: Dictates the order in which the encoding/encryption was applied.
        • ContentEncodingType: Set to 1 to explicitly signify encryption rather than compression.
        • ContentEncryption: The master container housing all encryption-specific settings for the track.

Key Identifiers via ContentEncKeyID

Inside the ContentEncryption element, the most critical element for key mapping is ContentEncKeyID.

ContentEncKeyID stores the raw binary representation of the Key Identifier (KID), typically a 16-byte (128-bit) value. This identifier does not contain the secret cryptographic key itself; instead, it acts as a public lookup token. When a player parses the container, it extracts the KID from ContentEncKeyID and communicates it through the browser's Encrypted Media Extensions (EME) layer to the underlying DRM CDM (such as Google Widevine or Microsoft PlayReady). The CDM uses this KID to request or locate the matching content key via the DRM license server.

Cipher and Mode Configuration

Alongside ContentEncKeyID, the ContentEncryption element declares the cryptographic algorithms required to process the track:

  • ContentEncAlgo: Identifies the encryption algorithm used. In standard WebM encryption, this value is set to 5 to denote AES (Advanced Encryption Standard).
  • ContentEncAesSettings: Defines specific operational settings for the AES cipher.
    • AESSettingsCipherMode: Set to 1 to specify AES-CTR (Counter Mode), which is standard for Common Encryption (CENC) compliance across streaming media.

Multi-Key and Track Separation

WebM container architecture supports multi-key workflows, where audio and video streams, or different video resolutions (such as SD, HD, and 4K), require separate cryptographic keys.

Because ContentEncodings and ContentEncKeyID are scoped directly to individual TrackEntry structures, the multiplexer assigns different KIDs to different tracks by simply placing distinct ContentEncKeyID binary payloads in each respective TrackEntry.

For instance, Track 1 (Video) can define a ContentEncKeyID mapped to a 4K-tier license, while Track 2 (Audio) defines a different ContentEncKeyID requiring a standard audio license. When the client demuxes the file, it reads the header, registers both KIDs, and retrieves separate decryption keys from the license response, decrypting each stream independently while processing the same encapsulated file.
