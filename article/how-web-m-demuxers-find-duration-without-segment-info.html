How WebM Demuxers Find Duration Without Segment Info

In standard WebM and Matroska (MKV) files, media duration is typically stored in the Duration element within the Segment Info EBML container. However, during live streaming, recording interruptions, or rapid encoding pipelines, this element is often omitted. When the Segment Info duration is absent, WebM demuxers must dynamically estimate or calculate the total duration by inspecting the file index, seeking to the final clusters, parsing frame-level timestamps, or reading stream-specific container properties.

1. Using the Cues Element (Index Table)

If the file contains a Cues element—the index structure used for seeking—the demuxer will parse the last available CuePoint.

  1. Locate Last Cue: The demuxer reads the last CuePoint to extract its CueTime and the byte offset of the corresponding Cluster.
  2. Seek to Cluster: The demuxer seeks directly to that cluster, parses the Cluster timestamp, and reads all nested SimpleBlock or BlockGroup elements.
  3. Calculate Timestamp: It finds the block with the highest timestamp within that final cluster and adds that block’s individual duration to finalize the total playback length.

Because the Cues element usually resides near the beginning or end of the file, this method avoids scanning the entire container and requires only minimal I/O operations.

2. Reverse File Seeking and Final Cluster Parsing

If both the Duration field and the Cues table are missing, a seekable demuxer (such as those in FFmpeg, GStreamer, or modern web browsers) will perform a reverse scan from the end of the file.

  1. Scan for Cluster ID: Starting from the end of the file, the demuxer reads backward in chunks (typically 32KB to 64KB) searching for the standard EBML Cluster ID (0x1F43B675).
  2. Read Base Cluster Timestamp: Upon finding the last valid cluster, the demuxer parses the Timestamp (or legacy Timecode) element, which establishes the baseline time for all blocks within that cluster.
  3. Inspect Blocks: The demuxer parses every SimpleBlock or BlockGroup inside that cluster to identify the largest relative block timecode.
  4. Formula: The final presentation time is calculated as: \[\text{Final PTS} = (\text{Cluster Timestamp} + \text{Block Relative Timestamp}) \times \text{TimestampScale}\]

3. Estimating the Final Frame Duration

Finding the presentation timestamp (PTS) of the last block gives the start time of the final frame, not the total container duration. To compute the exact total duration, the demuxer must account for the display length of that final frame using one of several fallbacks:

  • DefaultDuration Element: Demuxers check the TrackEntry in the segment header. If DefaultDuration is set (common for fixed-frame-rate video), this value is added directly to the last block's PTS.
  • Audio Packet Size: For audio tracks, demuxers decode or inspect the final audio packet header to determine the number of samples, calculating duration via the track's sampling frequency.
  • Codec Bitstream Metadata: If the container lacks hints, demuxers may parse codec headers (such as VP8, VP9, or AV1 sequence headers) to detect frame-rate flags.
  • Preceding Frame Duration: If all metadata is absent, demuxers estimate the last frame's duration based on the delta between the last two frames.

4. Dynamic Tracking for Non-Seekable Streams

When a WebM file is streamed over a pipe, network socket, or chunked HTTP connection without seek capabilities, demuxers cannot jump to the end of the file. In these scenarios:

  • The demuxer initializes the playback session with duration set to unknown, infinite, or NaN.
  • As the stream plays, the demuxer continuously updates an internal "current maximum duration" based on the highest PTS observed so far.
  • The total duration is only finalized once the demuxer encounters the End of File (EOF) or the final cluster terminator.
