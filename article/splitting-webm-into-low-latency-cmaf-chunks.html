Splitting WebM into Low-Latency CMAF Chunks

Modern live streaming workflows increasingly ingest WebM/WebRTC sources and repackage them for scalable distribution via Common Media Application Format (CMAF). This article explains the technical mechanics of how media processing engines ingest continuous WebM streams, demux their Matroska-based containers, process the underlying elementary streams, and dynamically package the media into fragmented MP4 (fMP4) chunks compatible with ultra-low-latency (ULL) delivery pipelines.

1. Ingestion and EBML Demuxing

WebM is a subset of the Matroska (MKV) container format built on Extensible Binary Meta Language (EBML). In a real-time ingestion pipeline, the streaming engine receives a continuous byte stream containing EBML elements:

  • Segment Information and Tracks: Identifies codecs, sample rates, and video resolutions.
  • Clusters and SimpleBlocks: Encapsulate compressed video frames and audio packets along with local timecodes.

Unlike file-based demuxers that require an entire file index (Cues), streaming engines process EBML elements sequentially as a continuous stream. The demuxer extracts raw access units (encoded video frames and audio samples) and normalizes timestamps into continuous Presentation Time Stamps (PTS) and Decode Time Stamps (DTS).

2. Codec Alignment and Transmuxing

WebM typically encapsulates VP8, VP9, or AV1 for video, and Opus for audio. CMAF is codec-agnostic but strictly standardized:

  • Passthrough (Transmuxing): If the WebM stream uses AV1 or VP9 video and Opus or AAC audio, the engine can pass the compressed packets directly into the CMAF container without re-encoding, preserving low processing latency.
  • Transcoding: If the target CMAF profile requires H.264/AVC (for broad Apple/HLS compatibility) or AAC audio, the engine routes raw frames through hardware-accelerated encoders (e.g., NVENC, QuickSync) with zero-latency buffer configurations and fixed Group of Pictures (GOP) lengths.

3. fMP4 Fragmentation and CMAF Encapsulation

CMAF structures media into fragmented MP4 containers consisting of an initialization segment and a sequence of media fragments:

  • Initialization Segment (init.mp4): Contains the File Type Box (ftyp) and Movie Box (moov), defining track metadata and codec configurations.
  • Media Segments: Composed of Movie Fragment Boxes (moof) and Media Data Boxes (mdat). The moof box contains sample duration, size, flags, and byte offsets via mfhd, traf, and trun boxes, while the mdat contains the actual compressed media payload.

4. Splitting into Ultra-Low-Latency CMAF Chunks

To achieve sub-second latency, media engines do not wait for an entire media segment (typically 2–6 seconds) to finish encoding. Instead, they divide segments into smaller units called CMAF Chunks:

  • Chunk Composition: A CMAF chunk consists of an individual moof + mdat pair containing a subset of frames (often as short as a single frame or a 200–500ms slice of video/audio).
  • Chunk Generation: As soon as an encoder finishes a frame or small set of frames, the engine writes the relative timing into a moof header, appends the raw frame into mdat, and pushes the chunk directly to the HTTP server.
  • HTTP Chunked Transfer Encoding (CTE): The web server streams these individual fMP4 chunks using CTE (Transfer-Encoding: chunked). Downstream players can begin downloading and decoding parts of a segment before the full segment has finished broadcasting.

5. Manifest and Time Synchronization

While chunks are continuously streamed over HTTP, the engine updates playlist files in real time:

  • LL-DASH: Uses availability time offsets to advertise the availability of partial segments.
  • LL-HLS: Advertises partial segments using the EXT-X-PART tag and sends preload hints (EXT-X-PRELOAD-HINT) so players can request upcoming chunks in advance.

This combination of streaming EBML parsing, single-frame or sub-second fMP4 encapsulation, and chunked HTTP transport allows engines to bridge WebM sources into ultra-low-latency CMAF workflows with minimal overhead.
