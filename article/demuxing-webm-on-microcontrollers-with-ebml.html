Demuxing WebM on Microcontrollers with EBML

This article explores how resource-constrained microcontrollers can demux WebM media streams by implementing lightweight Extensible Binary Meta Language (EBML) parsing techniques. Because typical microcontrollers feature limited RAM—often ranging from a few kilobytes to a couple of megabytes—standard tree-based EBML decoders are unfeasible. By relying on stream-oriented finite state machines, selective element skipping, optimized Variable-Length Integer (VINT) decoding, and ring-buffered I/O, developers can extract audio and video payloads from WebM files on low-power embedded hardware in real time.

Stream-Oriented Finite State Machines

Standard desktop EBML parsers build an Abstract Syntax Tree (AST) of the container hierarchy in memory. On a microcontroller, allocating dynamic trees quickly exhausts the heap.

A stream-oriented parser uses a Finite State Machine (FSM) that processes bytes sequentially from a network socket, SD card, or flash storage. The parser tracks only the current depth and parent element boundaries through an internal stack of offsets. Instead of buffering an entire container, the parser evaluates element headers byte by byte, changes states (such as READ_ID, READ_SIZE, PROCESS_PAYLOAD, or SKIP_PAYLOAD), and pushes payload data directly to downstream hardware decoders or buffers.

In-Place VINT Decoding

EBML elements use Variable-Length Integers (VINTs) for both Element IDs and Data Sizes. A VINT encodes its length using leading zeros followed by a marker bit:

  • 1xxxxxxx indicates a 1-byte length.
  • 01xxxxxx indicates a 2-byte length.
  • 001xxxxxx indicates a 3-byte length, continuing up to 8 bytes.

To minimize memory overhead, parsing should decode these values iteratively using simple bitwise shifts instead of caching byte sequences into intermediary memory structures. A lightweight decoder only requires an accumulator variable and a byte counter. Once the initial byte reveals the length via the __builtin_clz (count leading zeros) instruction, remaining bytes are shifted into a 64-bit integer on the fly.

Selective Whitelisting and Non-Seeking Payload Skipping

WebM files contain various auxiliary elements that microcontrollers do not need for continuous playback, such as SeekHead, Cues, Tags, and metadata strings.

A low-memory parser utilizes an element whitelist containing only fundamental tokens:

  • EBML header and Segment (for container validation)
  • Tracks and TrackEntry (to identify codec types, timecode scales, and stream indexes)
  • Cluster, Timecode, and SimpleBlock / BlockGroup (for media payloads)

When an Element ID is encountered that is not in the whitelist, the parser reads the declared data size and increments a skip-counter. The microcontroller bypasses this data without allocating buffer space by advancing the hardware SPI/SD bus clock or reading directly into a small, reusable scratchpad.

Zero-Copy Frame Extraction from SimpleBlocks

The SimpleBlock contains the raw video frame or audio packet. The header of a SimpleBlock contains:

  1. Track Number (VINT)
  2. Relative Timecode (signed 16-bit integer)
  3. Flags (lacing, keyframe, discardable)

Rather than copying the entire frame into an intermediate RAM buffer, the parser strips the small header (typically 4 to 12 bytes) and passes the memory pointer or direct DMA transfer channel of the remaining payload directly to the peripheral responsible for decoding (e.g., an external audio DAC or hardware codec).

Handling Unknown/Indefinite Element Lengths

Live WebM streams or memory-efficient encoders often write Cluster elements with unknown data lengths (a VINT filled with 1 bits). An embedded parser cannot rely on a pre-calculated byte offset to know when an unknown-length container ends.

To handle this efficiently without back-buffering:

  • Maintain a parser state that treats unknown-length containers as infinite streams.
  • Detect the termination of the current container by continuously evaluating incoming Element IDs at the expected boundary.
  • When the parser encounters a top-level ID (such as a new Cluster ID 0x1F43B675), it automatically resolves and terminates the context of the previous cluster, resetting local timecodes without retaining prior stream history.
