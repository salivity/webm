WebM Non-Square Pixel Aspect Ratio Guide

WebM players determine the correct aspect ratio for video containing non-square pixels primarily by reading the display dimensions embedded in the container's metadata and scaling the decoded frame accordingly. Because digital displays use square pixels, content originally recorded or mastered with anamorphic (non-square) pixels must be rescaled during playback. This article details the container elements, bitstream headers, calculation formulas, and precedence rules WebM players use to render the correct Display Aspect Ratio (DAR).

Container-Level Signaling

WebM is a restricted subset of the Matroska (MKV) container format. The container metadata provides the primary instructions for handling pixel geometry through specific elements within the TrackEntry -> Video master element:

  • PixelWidth & PixelHeight: These define the raw, coded video dimensions (Storage Aspect Ratio or SAR), representing the actual matrix of pixels stored in the video frames.
  • DisplayWidth & DisplayHeight: These specify the intended dimensions on screen. If non-square pixels are present, these values will not share the same ratio as PixelWidth and PixelHeight.
  • DisplayUnit: Indicates the measurement unit for DisplayWidth and DisplayHeight (default is 0, representing pixels).

When a WebM player demuxes the file, it extracts these values before initializing the video renderer.

Codec Bitstream Signaling

WebM supports video codecs such as VP8, VP9, and AV1. These codecs can also carry Sample Aspect Ratio (SAR) or Pixel Aspect Ratio (PAR) information inside their sequence headers:

  • VP8: Contains horizontal and vertical scale factors within the frame header.
  • VP9: Includes a render size field in the frame header that indicates the desired output resolution independent of the coded resolution.
  • AV1: Supports explicit render_width and render_height syntax, or sample aspect ratio flags within the sequence header.

Order of Precedence in WebM Players

Standard WebM compliant players (including web browsers like Chromium and Firefox, as well as media frameworks like FFmpeg and GStreamer) follow a specific hierarchy when determining the aspect ratio:

  1. Container Metadata (Matroska Level): DisplayWidth and DisplayHeight in the Matroska header take highest precedence. If set, the player uses these to determine the output geometry.
  2. Bitstream Headers (Codec Level): If the container does not specify distinct display dimensions, or if they match the pixel dimensions by default, the player inspects the codec's internal header flags (e.g., VP9 render size).
  3. Square Pixel Fallback (1:1 PAR): If neither the container nor the codec specifies non-square pixel metadata, the player assumes a 1:1 Pixel Aspect Ratio, displaying the video at PixelWidth:PixelHeight.

The Aspect Ratio Calculation

To render the video accurately on a standard display, the player calculates the scaling factor using the relationship between the Storage Aspect Ratio (SAR), Pixel Aspect Ratio (PAR), and Display Aspect Ratio (DAR):

\[\text{DAR} = \frac{\text{DisplayWidth}}{\text{DisplayHeight}}\]

\[\text{PAR} = \frac{\text{DisplayWidth} \times \text{PixelHeight}}{\text{DisplayHeight} \times \text{PixelWidth}}\]

During rendering, the player decodes the raw frame into a pixel buffer of size PixelWidth \(\times\) PixelHeight. The graphics subsystem then maps this texture to an output viewport sized according to the calculated \(\text{DAR}\), applying horizontal or vertical interpolation (scaling) to correct for the non-square pixels.
