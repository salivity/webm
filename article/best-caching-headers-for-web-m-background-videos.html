Best Caching Headers for WebM Background Videos

Static WebM background videos can quickly consume substantial bandwidth and degrade page load speeds if not cached properly. This article outlines the most effective HTTP headers to configure for static WebM video assets, ensuring minimal server load, seamless byte-range streaming, and maximum performance across browsers and Content Delivery Networks (CDNs).

1. Cache-Control

The Cache-Control header defines how long and where the video file should be stored. Because background videos are typically large and rarely change, long-term caching is recommended.

  • For Versioned/Hashed Filenames (Recommended): If your build pipeline appends a unique hash to the video URL (e.g., hero-background.v1.a8f2d.webm):

    Cache-Control: public, max-age=31536000, immutable
    • public: Allows browsers, proxies, and CDNs to cache the response.
    • max-age=31536000: Caches the file for one year (in seconds).
    • immutable: Tells the browser the file will never change, eliminating conditional revalidation requests on page refreshes.

  • For Fixed/Unversioned Filenames: If the file URL remains static (e.g., background.webm), use a shorter TTL paired with revalidation:

    Cache-Control: public, max-age=604800, stale-while-revalidate=86400
    • max-age=604800: Caches the asset for 7 days.
    • stale-while-revalidate=86400: Allows serving a stale version for an extra day while the browser asynchronously fetches the newest version in the background.

2. Accept-Ranges

Browsers load video files progressively using HTTP range requests rather than downloading the entire asset at once.

Accept-Ranges: bytes
  • Explicitly informs the browser that the server supports partial content requests (HTTP 206 Partial Content).
  • Crucial for video rendering; without it, browsers must download the entire video before playing it.

3. ETag and Last-Modified

Validation headers enable conditional requests when a cached item expires, allowing the server to return a lightweight 304 Not Modified status rather than re-transmitting the entire video.

ETag: "63a8f-5b12345678900"
Last-Modified: Wed, 21 Oct 2023 07:28:00 GMT
  • ETag: A unique hash representing the current version of the file.
  • Last-Modified: The timestamp of when the file was last updated on the origin server.

4. Content-Type and Compression

Ensure the server identifies the MIME type correctly and avoids redundant compression:

  • MIME Type: 
    Content-Type: video/webm
  • Avoid Compression: Do not apply Gzip or Brotli compression to WebM files. WebM is already heavily compressed; enabling gzip or brotli adds CPU overhead and can break byte-range streaming without providing meaningful size reductions.

Example Production Header Set

A complete header response for an immutable, static WebM background video:

HTTP/1.1 200 OK
Content-Type: video/webm
Content-Length: 2458901
Accept-Ranges: bytes
Cache-Control: public, max-age=31536000, immutable
ETag: "video-hash-7890abc"
Last-Modified: Mon, 15 Jan 2024 12:00:00 GMT
