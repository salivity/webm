VP9 Superblock Partitioning in WebM SimpleBlocks

This article explains how the VP9 video codec organizes, partitions, and signals its 64x64 superblocks within the data payload of a WebM SimpleBlock. It covers the path from container-level frame encapsulation in EBML down to the recursive quadtree partitioning syntax read by VP9’s boolean arithmetic entropy decoder.

1. The WebM SimpleBlock Container Layer

A WebM file uses the Extensible Binary Meta Language (EBML) format. Video frames are encapsulated inside SimpleBlock elements within a Cluster.

A SimpleBlock has a compact header followed directly by the raw VP9 frame bitstream:

  • Track Number: EBML variable-length integer (VINT) indicating the video track.
  • Relative Timecode: Signed 16-bit integer relative to the parent Cluster timestamp.
  • Flags: An 8-bit field containing frame attributes (Keyframe flag, Discardable, Lacing, etc.).
  • Payload: The raw byte payload containing the VP9 compressed frame.

The container does not interpret the internal macroblock or superblock structure; it merely passes the raw payload directly to the VP9 decoder.

2. VP9 Frame Structure and Tiles

Once the payload is passed to the VP9 decoder, it is parsed into two main segments:

  1. Uncompressed Header: Contains global parameters such as frame dimensions, bit-depth, frame type (Keyframe or Interframe), and tile layout (column and row counts).
  2. Compressed Header & Tile Data: Contains entropy-coded probability updates followed by the actual tile data.

A frame is split into independent tiles. Each tile processes a sequence of Superblocks (SBs) in raster-scan order.

3. Superblock (64x64) Hierarchy

The fundamental coding unit in VP9 is the Superblock (SB64), which covers a \(64 \times 64\) luma pixel area (and corresponding chroma pixels based on the sub-sampling format).

Each \(64 \times 64\) block is recursively partitioned using a quadtree structure down to a minimum block size of \(8 \times 8\) (which can further split into \(4 \times 4\) sub-blocks for transform/prediction purposes).

At each level of the tree (from \(64 \times 64\) down to \(16 \times 16\)), the encoder can choose one of four partition modes:

  • PARTITION_NONE: The block is coded as a single unit of the current size (e.g., \(64 \times 64\)).
  • PARTITION_HORZ: The block is split horizontally into two equal rectangular blocks (e.g., two \(64 \times 32\) blocks).
  • PARTITION_VERT: The block is split vertically into two equal rectangular blocks (e.g., two \(32 \times 64\) blocks).
  • PARTITION_SPLIT: The block is split into four equal sub-quadrants (e.g., four \(32 \times 32\) blocks), triggering recursion for each sub-block.

4. Signaling Partition Decisions via the Bool-Coder

VP9 encodes all superblock partition decisions using a custom non-binary arithmetic coder called the Bool-coder.

Context-Dependent Modeling

The partition mode is not encoded using fixed-length bits. Instead, it uses a 4-symbol probability context determined by the partition sizes of the above and left neighboring blocks:

  • A context index is derived from whether the adjacent blocks are larger, smaller, or equal to the current block size.
  • The decoder fetches the corresponding cumulative distribution / probability array (partition_probs[context_index]).

Parsing the Partition Tree

The syntax for partitioning at any given node \(N\) proceeds as follows:

  1. Boundary Checks: If the current block extends beyond the frame edge (bottom or right boundary), the partition choice is restricted. If both horizontal and vertical boundaries are exceeded, a PARTITION_SPLIT is inferred automatically without reading bits from the stream. If only one edge is exceeded, the stream signals whether to split or adapt to the boundary without full 4-way signaling.
  2. Standard Tree Reading: If completely inside the frame:
    • The bool-coder decodes a symbol \(S \in \{0, 1, 2, 3\}\) mapping to NONE, HORZ, VERT, or SPLIT.
  3. Recursive Descent:
    • If PARTITION_SPLIT is decoded and the current block size is larger than \(16 \times 16\), the decoder immediately recurses into the top-left, top-right, bottom-left, and bottom-right sub-blocks.
    • If the block size reaches \(8 \times 8\), a split produces four \(4 \times 4\) prediction sub-blocks.

5. Decoding Execution Flow

Inside the SimpleBlock payload, the complete signaling chain for superblocks operates as follows:

[WebM SimpleBlock Payload]
   └─► [VP9 Frame Header]
         └─► [Tile Data Segment]
               └─► [Initialize Bool-Coder for Tile]
                     └─► Loop over Superblocks (Raster Order):
                           └─► Parse Partition Tree (Contextual Bool-Coder)
                                 ├─ 64x64 -> SPLIT
                                 │    ├─ 32x32 Sub-block 0 -> NONE
                                 │    ├─ 32x32 Sub-block 1 -> HORZ (two 32x16)
                                 │    ├─ 32x32 Sub-block 2 -> VERT (two 16x32)
                                 │    └─ 32x32 Sub-block 3 -> SPLIT ...
                                 └─► Read Prediction Modes & Transform Coefficients

Once a terminal block size is reached, the decoder immediately reads the prediction modes (Intra/Inter), motion vectors, and quantized DCT/ADST transform coefficients for that block before proceeding to the next block in the tree.
