WebM Video Decode Interrupts in Mobile SoCs

Modern mobile system-on-chips (SoCs) accelerate WebM video playback—powered by VP8, VP9, or AV1 codecs—by offloading bitstream processing to dedicated Video Processing Units (VPUs). When hardware-accelerated decoding finishes for a single frame, the VPU asserts a dedicated Shared Peripheral Interrupt (SPI) routed to the main CPU through an interrupt controller, such as the ARM Generic Interrupt Controller (GIC). This article explains the interrupt architecture, specific vendor implementations (such as Qualcomm, Samsung, and MediaTek), and the hardware-to-software register handshake that notifies the operating system of a completed WebM decode.

The Role of the VPU in WebM Decoding

WebM containers encapsulate video streams compressed with VP8, VP9, or AV1 profiles. Because running entropy decoding, inverse discrete cosine transforms, loop filtering, and motion compensation entirely in software drains the battery rapidly, mobile SoCs deploy dedicated hardware macro-blocks.

The application layer sends the compressed WebM bitstream through a framework (such as Android MediaCodec or Linux V4L2) down to the kernel driver. The driver places the bitstream into Direct Memory Access (DMA) buffers and writes to the VPU control registers to begin decoding. The CPU then relinquishes control and enters an idle or power-saving state while the VPU operates autonomously.

The Interrupt Mechanism: ARM GIC and SPIs

Mobile hardware decoders do not poll registers to confirm a frame has rendered; doing so would waste significant CPU cycles. Instead, they rely on hardware interrupts:

  1. Hardware Assertion: Once the VPU reconstructs the YUV frame and writes it via DMA into destination memory, the hardware logic transitions an output line to high (level-sensitive) or pulses it (edge-triggered).
  2. Interrupt Routing: This physical electrical trace enters the ARM Generic Interrupt Controller (GIC) configured as a Shared Peripheral Interrupt (SPI).
  3. Interrupt Service Routine (ISR): The GIC signals the primary CPU, pausing non-critical execution to jump to the registered kernel VPU driver's ISR.

Vendor-Specific Implementations

While all standard mobile SoCs route interrupts via the GIC, the specific peripheral blocks, drivers, and interrupt signatures depend on the vendor:

  • Qualcomm Snapdragon (Venus / Iris VPU): Qualcomm SoCs use dedicated video cores known as Venus or Iris. The hardware signals frame completion through a unified interrupt line connected to the GIC. Internally, Venus uses a RISC microcontroller running proprietary firmware that manages the Host Firmware Interface (HFI). When a VP8, VP9, or AV1 frame finishes, the microcontroller sends an HFI_EVENT_FRAME_DONE response into a shared memory queue and fires the hardware interrupt line, prompting the kernel venus_isr to parse the packet.
  • Samsung Exynos (MFC - Multi-Format Codec): Exynos chips rely on the proprietary Multi-Format Codec (MFC) IP block. Upon finishing frame reconstruction and in-loop deblocking, the hardware asserts the MFC_INT interrupt. The Linux driver handler checks the interrupt status register (S5P_FIMV_SI_INT_STATUS), looking specifically for the MFC_PIC_DONE or MFC_FRAME_DONE status bit.
  • MediaTek Dimensity (VDEC): MediaTek SoCs utilize the VDEC engine managed by the mtk-vcodec driver. The VPU asserts a dedicated VDEC_IRQ line mapped to the GIC. The driver checks the hardware status registers for a bit signaling decode success or a reference picture failure before clearing the line.
  • Rockchip / VeriSilicon (Hantro / RKVDEC): Many lower-power mobile and embedded SoCs use VeriSilicon Hantro IP. These decoders feature an IRQ line mapped to a frame-ready flag. Once the frame pipeline clears, the hardware raises an interrupt, and the driver checks the DEC_READY or DEC_IRQ bit in the decoder status register.

The Hardware Handshake and Buffer Handoff

The assertion of the interrupt triggers a clear sequence to prevent deadlocks:

  1. Read Status Register: The CPU reads the VPU's internal Interrupt Status Register over the internal bus (such as AXI/AHB) to verify that the interrupt represents a completed picture (Picture Done / Slice Done) rather than an error condition (bitstream corruption or memory timeout).
  2. Clear Interrupt: The driver performs an acknowledgment write to the status register (often a "Write 1 to Clear" operation), de-asserting the physical interrupt line at the GIC level.
  3. Buffer Release: The kernel updates buffer tracking, marking the decoded YUV frame buffer as ready for consumption by the display subsystem or GPU (via SurfaceFlinger or DRM/KMS).
  4. Queue Next Frame: If subsequent WebM packets are available in the input ring buffer, the driver triggers the VPU registers again to initiate the next frame decode.
