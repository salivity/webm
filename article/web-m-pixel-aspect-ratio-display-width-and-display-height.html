WebM Pixel Aspect Ratio DisplayWidth and DisplayHeight

The WebM container format does not feature a dedicated, standalone metadata tag to define Pixel Aspect Ratio (PAR). Instead, WebM derives PAR indirectly through the relationship between encoded storage dimensions (PixelWidth and PixelHeight) and rendering target dimensions (DisplayWidth and DisplayHeight). By defining the final intended Display Aspect Ratio (DAR) via these display elements, media players can calculate the exact pixel stretching required to present non-square pixels correctly on a display device.

The WebM Video Track Dimensions

WebM inherits its video track specifications from the Matroska (EBML) specification. Within a video track header (TrackEntry -> Video), two pairs of elements dictate how the frame is stored and how it must be rendered:

  • PixelWidth and PixelHeight: These unsigned integer elements represent the raw, encoded resolution of the video stream in actual pixels (Storage Aspect Ratio, or SAR).
  • DisplayWidth and DisplayHeight: These unsigned integer elements define the intended spatial dimensions of the video when scaled for playback.

By default, if DisplayWidth or DisplayHeight are omitted from the WebM header, playback engines assume they are equal to PixelWidth and PixelHeight, which results in a 1:1 square pixel aspect ratio.

Calculating PAR from Display Elements

The Pixel Aspect Ratio represents the width-to-height ratio of an individual pixel. When video is encoded with non-square pixels (such as anamorphic NTSC or PAL DVD transfers), the storage resolution does not match the viewing aspect ratio.

The relationship between Display Aspect Ratio (\(DAR\)), Storage Aspect Ratio (\(SAR\)), and Pixel Aspect Ratio (\(PAR\)) is defined mathematically as:

\[\text{DAR} = \text{SAR} \times \text{PAR}\]

Because WebM provides the display dimensions and pixel dimensions directly, media players calculate the PAR using the following formula:

\[\text{PAR} = \frac{\text{DisplayWidth} \times \text{PixelHeight}}{\text{DisplayHeight} \times \text{PixelWidth}}\]

Practical Calculation Example

Consider an anamorphic standard-definition video encoded for widescreen playback:

  • PixelWidth: 720
  • PixelHeight: 480
  • DisplayWidth: 854
  • DisplayHeight: 480

Using the calculation:

\[\text{PAR} = \frac{854 \times 480}{480 \times 720} = \frac{854}{720} \approx 1.186\]

The player reads this container metadata and horizontally scales each horizontal pixel by a factor of roughly 1.186 during playback to display the full 16:9 picture without vertical compression.

The Role of the DisplayUnit Element

The interpretation of DisplayWidth and DisplayHeight is governed by another optional element: DisplayUnit.

  • Value 0 (Pixels): This is the default setting. DisplayWidth and DisplayHeight indicate the preferred target resolution in pixels.
  • Value 1 (Centimeters): Defines physical display size in centimeters.
  • Value 2 (Inches): Defines physical display size in inches.
  • Value 3 (Display Aspect Ratio): Directs the demuxer to interpret the numbers in DisplayWidth and DisplayHeight purely as an aspect ratio fraction (for instance, 16 and 9) rather than specific target pixel bounds.

Regardless of whether DisplayUnit is set to 0 or 3, the ratio between DisplayWidth and DisplayHeight remains the reference for calculating the necessary non-square pixel scaling.

Container vs. Codec Precedence

Codecs commonly encapsulated within WebM—such as VP8, VP9, and AV1—can also signal aspect ratio information inside their sequence headers. However, the WebM container specification mandates that container-level track properties take precedence over elementary bitstream headers. Demuxers and playback renderers rely on DisplayWidth and DisplayHeight in the EBML structure to override internal codec geometry, ensuring that pixel aspect ratio adjustments remain consistent across varying decoder implementations.
